### 📝 Web3 响应式：从静态页面到实时 DApp

1\. 核心矛盾：异步链上数据 vs 同步 UI 渲染

-   **挑战**：区块链是“拉取（Pull）”模式。你的代币余额存在节点里，前端无法直接感知余额变了，除非主动去查。
    
-   **响应式方案**：建立一套机制，当“链上状态”发生变化时，自动触发“前端状态”更新，从而驱动 UI 重新渲染。
    

2\. 监听器模式 (The Listener Pattern)

这是响应式的技术底座。

-   **Provider 订阅**：使用 provider.on("block", ...) 监听每一个新块。
    
-   **事件监听 (Event Logs)**：针对特定合约监听 emit 出来的事件。
    
    -   _场景_：当用户完成一次 Swap，合约抛出事件，前端监听到后立即刷新余额。
        
    -   _笔记技巧：这是响应式更新最快、最节省资源的方式。_
        

3\. Wagmi & TanStack Query：响应式的工业标准

-   **自动重刷 (Auto-refetching)**：当钱包切换账号或网络时，useAccount 和 useBalance 等 Hook 会自动检测并重新获取数据。
    
-   **状态管理**：它将链上数据转化为 React 的 state（例如 data, isLoading, isError）。
    
    -   _核心逻辑_：数据一旦从 RPC 返回，React 会感知到变量变化，页面自动“闪变”更新。
        

4\. 轮询 (Polling) —— 简单粗暴的响应式

如果合约没有抛出事件，或者你需要实时监控价格，通常使用轮询。

-   **逻辑**：每隔N 秒执行一次 eth\_call。
    
-   **优化策略**：
    
    -   **窗口聚焦检测**：只有当用户正看着网页时才轮询，切换到后台就停止，节省 RPC 额度。
        
    -   **指数退避**：如果多次失败，则拉长请求间隔。
        

5\. Multicall：响应式的性能加速器

当一个页面有 10 个响应式变量（余额、价格、授权额度等），如果不优化，浏览器会瞬间发出 10 个请求，导致页面卡顿。

-   **原理**：将多个查询请求打包成一个巨大的 eth\_call 发送给节点。
    
-   **响应式价值**：整个页面的所有数据在同一个区块高度同步更新，避免了页面上数据“各变各的”导致的不一致感。
    

6\. 乐观更新 (Optimistic Updates) —— “假的”响应式

这是 Web3 用户体验（UX）的最高级技巧。

-   **痛点**：用户点击转账，要等 12 秒区块确认后 UI 才变，用户会焦虑。
    
-   **响应式方案**：在交易发出但**尚未确认**时，前端直接把余额减去，并显示“成功”。
    
-   **回滚逻辑**：如果交易最后失败了，再根据报错把余额加回来。
    
-   _笔记技巧：这让 DApp 用起来像传统 App 一样流畅。_

### 📝 Uniswap 核心知识点笔记

1\. 核心定义：AMM (Automated Market Maker)

-   **传统交易所（CEX）**：使用“订单簿（Order Book）”模式，需要买家和卖家挂单匹配。
    
-   **Uniswap (DEX)**：使用“自动做市商（AMM）”模式。它没有订单簿，交易是直接与\*\*流动性池（Liquidity Pool）\*\*进行的。
    
-   **核心逻辑**：只要池子里有钱，你随时可以换，不需要等待对手方。
    

2\. 灵魂公式：恒定乘积公式 (

```
        x⋅y=kx \cdot y = kx⋅y=k
      
```

)

这是 Uniswap V2 的数学基础：

```
        xxx
      
```

：池子中资产 A 的数量。

```
        yyy
      
```

：池子中资产 B 的数量。

```
        kkk
      
```

：常数（在交易过程中保持不变）。

-   **原理**：当你买入 A 时，
    
    ```
            xxx
          
    ```
    
    减少，为了保持
    
    ```
            kkk
          
    ```
    
    不变，
    
    ```
            yyy
          
    ```
    
    必须增加。这就导致 A 的价格相对于 B 上升。
    
    -   _笔记技巧：交易量越大，价格变动（滑点）越大。_
        

3\. 关键角色：流动性提供者 (LP - Liquidity Provider)

-   **做啥的**：任何人都可以向池子中存入等价值的两种代币（例如 ETH 和 USDT）。
    
-   **奖励**：作为回报，LP 会获得交易手续费的分成。
    
-   **凭证**：存入资金后，LP 会获得 **LP Token**（ERC-20 票据），代表其在池子中的份额。
    

4\. 无常损失 (Impermanent Loss)

-   **定义**：这是 LP 面临的最大风险。
    
-   **现象**：当池子里的代币价格发生大幅偏离时，LP 提取资金时的总价值，会低于他当初直接持有这些代币（HODL）的价值。
    
-   _笔记技巧：价格波动越大，无常损失越严重。如果价格回到初始点，损失消失。_
    

5\. Uniswap V2 vs V3 (分水岭)

-   **V2 (全量流动性)**：资金分布在
    
    ```
            [0,∞][0, \infty][0,∞]
          
    ```
    
    整个价格区间。资金利用率极低（大部分资金在成交价很远的地方躺平）。
    
-   **V3 (集中流动性 - Concentrated Liquidity)**：LP 可以选择特定的价格区间（例如 ETH 在
    
    ```
            2000−2000-2000−
          
    ```
    
    2500 之间提供流动性）。
    
    -   **优点**：极大地提高了资金利用率。
        
    -   **变化**：LP Token 不再是 ERC-20，而是变成了 **ERC-721 (NFT)**，因为每个人的区间都不一样。
        

6\. 价格预言机 (TWAP)

-   Uniswap 不仅是交易所，还是**价格来源**。
    
-   **TWAP (Time-Weighted Average Price)**：时间加权平均价格。它通过记录多个区块的价格并取平均值，防止黑客通过单笔大额交易操纵瞬时价格（防范闪电贷攻击）。
    

7\. 开发者必知：Router 与 Factory

如果你要在代码里调用 Uniswap：

-   **Factory 合约**：负责创建新的交易对（Pairs），管理所有的池子。
    
-   **Router 合约**：开发者最常用的接口。处理“我要换币（Swap）”、“我要加钱（Add Liquidity）”等逻辑。
    
    -   _常用函数：swapExactTokensForTokens (用确定的 A 换尽量多的 B)_

### 📘 核心知识点：多级路径路由（Multi-hop Routing）

1\. 业务痛点：流动性孤岛

在链上，并非任意两种代币之间都有直接的流动性池（Pair）。

-   **场景：** 用户持有代币 A，想换成代币 C，但全网只有 A/B 和 B/C 两个池子。
    
-   **传统痛点：** 用户若手动分两次交易（A→B，再 B→C），不仅操作繁琐，还需支付两笔高昂的 Gas 费，且面临两次滑点风险，体验极差。
    

2\. 技术方案：Universal Router 的自动寻路

Uniswap 引入了\*\*路由合约（Router）\*\*来屏蔽底层的复杂性。

-   **核心逻辑：** 路由系统在后台自动搜索所有可用池子，寻找损耗最小的路径。例如：A -> WETH -> USDC -> C。
    
-   **底层映射：** 作为 **后端**，你需要敏锐地察觉到，这本质上是一个经典的**图论问题**。
    
    -   **节点（Node）：** 每种代币（Token）。
        
    -   **边（Edge）：** 流动性池（Liquidity Pool）。
        
    -   **权重（Weight）：** 池子深度、手续费及实时汇率。
        

3\. CEX 后端开发者的视角

未来你在交易所负责**撮合引擎**或**聚合交易**时，逻辑是高度一致的：

-   **离线计算优化：** 链上计算（On-chain）极其昂贵且缓慢。因此，最优路径的搜索必须在\*\*离线后端\*\*完成。
    
-   **高并发挑战：** 你的 Go 程序需要维护一个内存中的“动态权值图”，实时同步全链数万个池子的状态。当用户请求报价时，系统需在毫秒级通过 **Dijkstra** 或 **Bellman-Ford** 变体算法算出最优路径。
    
-   **原子性执行：** 算出路径后，后端将 Token 数组（Path）封装成指令交给合约，确保交易在“一跳”或“多跳”中原子化执行，要么全成功，要么全失败。

### 📘 知识点：Merkle Tree (默克尔树) —— 链下计算与链上验证的完美闭环

**1\. 痛点：链上存储太贵了**  
假设你要给 10,000 个用户发空投（Airdrop）或者做白名单。

-   **笨办法：** 在 Solidity 里写一个 mapping(address => bool)，把 10,000 个地址全写进去。
    
-   **代价：** Gas 费会爆炸。写入 10,000 个数据到 Storage，可能要花掉几十个 ETH。
    

**2\. 解决方案：只存一个“指纹” (Merkle Root)**  
Merkle Tree 是一种二叉树结构，它能把成千上万条数据，层层哈希（Hash），最后压缩成一个 **32 字节** 的字符串，叫做 **Merkle Root（根哈希）**。

-   **Go 后端的工作（链下）：**
    
    1.  拿到 10,000 个白名单地址。
        
    2.  构建一棵 Merkle Tree。
        
    3.  算出 **Root**。
        
    4.  为每一个用户生成属于他的 **Proof（默克尔证明，即通往根节点的路径数组）**。
        
-   **Solidity 合约的工作（链上）：**
    
    1.  只在 Storage 里存一个变量：bytes32 public root;（省钱省疯了！）。
        
    2.  提供一个 claim 函数，用户带着后端给的 Proof 来领奖。
        
    3.  合约通过 MerkleProof.verify() 计算验证：你的 Proof + 你的地址，算出来的根是不是等于我存的那个 Root？
        

**3\. 对交易所（CEX）后端的特殊意义：PoR (储备金证明)**  
FTX 暴雷后，所有 CEX 都在做 **Proof of Reserves**。

-   **逻辑：** 交易所如何证明“我真的有用户的钱”，但又不泄露“具体哪个用户有多少钱”？
    
-   **实现：**
    
    -   你的 **Go 后端** 把所有用户的余额做成叶子节点，生成一棵巨大的 Merkle Tree。
        
    -   公布 **Root** 和交易所链上钱包的总余额。
        
    -   **用户验证：** 用户在前端输入自己的 ID，后端给他返回一个 Proof。用户自己算一遍，发现自己的余额确实被包含在那棵树的 Root 里，且 Root 对应链上资产。
        

* * *

### 📝 笔记心得：

学了 Merkle Tree **才**明白，真正的工程化方案是 **“数据在链下，信任在链上”**。

-   **Go 端**：负责繁重的树构建和 Proof 生成（CPU 密集型，链下随便跑）。
    
-   **Solidity 端**：负责极简的验证逻辑（只存一个 Hash，Gas 极低）。
    

**一句话复记：**  
Merkle Tree 是区块链世界的“压缩机”。它让后端可以用极低的链上成本（32字节），验证近乎无限量的链下数据

### 📘 知识点：Flash Swaps (闪电兑换) 与“乐观转账”机制

**1\. 核心定义：先拿货，后给钱**  
在传统 CEX 或普通 DEX 中，交易逻辑是“一手交钱，一手交货”（原子交换）。  
**但是**，Uniswap 的 **Flash Swaps** 允许你：

-   **第一步：** 从 Uniswap 池子里**先把 Token 拿走**（比如拿走 1000 ETH）。
    
-   **第二步：** 拿着这笔钱去别的平台（比如 SushiSwap 或 Aave）做任何你想做的事（套利、清算）。
    
-   **第三步：** 在**同一笔交易**结束前，把钱还回来（或者支付对应的另一种 Token）。
    

**2\. 底层代码逻辑：乐观转账 (Optimistic Transfer)**  
这是面试时的加分项，你需要懂 Solidity层面的执行顺序：

-   **正常逻辑：** transferFrom(用户, 池子) -> transfer(池子, 用户)。
    
-   **Uniswap 逻辑：**
    
    1.  **Transfer：** 池子先把币转给用户（Optimistically，乐观地认为你会还）。
        
    2.  **Callback：** 池子调用用户合约的一个特定函数（V2叫 uniswapV2Call，V3叫 uniswapV3SwapCallback）。用户在这里执行自己的套利逻辑。
        
    3.  **Check：** Callback 执行完，池子检查自己的余额。**如果**余额没平（你没还钱），交易直接 **Revert**（回滚）。
        

**3\. 对后端/交易员的价值**

-   **无本套利：** 你的 Go 程序发现 Uniswap ETH 价格是 2000，SushiSwap 是 2010。你**不需要**自己持有 100 万美金本金。你可以用 Flash Swap 借出 Uniswap 的 ETH，卖给 SushiSwap，还完钱剩下的利润归你。
    
-   **CEX 充值逻辑差异：** 交易所的充值监听程序（Deposit Indexer）必须小心这种“内部交易”。因为 Flash Swap 可能会产生临时的余额变动，如果你的后端逻辑判断失误，可能会被复杂的调用链干扰。
    

* * *

Flash Swap 让你可以在支付之前就获得资产。它是 Uniswap 利用区块链“原子性”创造的金融奇迹，也是链上套利机器人的基石。

### 📘 知识点：TWAP —— 链上价格的“防弹衣”

**1\. 问题的由来：瞬时价格的脆弱性**  
在普通的 CEX（中心化交易所）里，价格由最后一笔成交价决定。**然后**你会发现，在 DeFi 里，如果直接拿 Uniswap 当前池子里的比例当价格，是非常危险的。

-   **黑客的操作：** 用闪电贷（Flash Loan）瞬间砸入 1 亿美金买入 ETH，导致池子比例瞬间失衡，ETH 价格在这一秒内暴涨 10 倍。
    
-   **后果：** 如果你的后端程序只看这一秒的价格，**就**会判定价格暴涨，从而错误地触发清算或者高位买入。
    

**2\. 解决方案：TWAP（时间加权平均价格）**  
Uniswap 为了解决这个问题，发明了 **累积价格（Cumulative Price）**。

-   **原理：** 它不直接存价格，而是存一个“价格 × 时间”的累积总和。
    
-   **逻辑：** 想要算出过去 10 分钟的平均价，你需要两个数据点：
    
    1.  现在的累积总和。
        
    2.  10 分钟前的累积总和。
        
-   **计算：** (现在的总和 - 10分钟前的总和) / 10分钟。
    

**3\. 为什么这对后端（Go）开发很重要？**  
当你写一个 Go 程序去同步价格时，你**才**会发现：你不能只调一个 getPrice() 函数，你得**手动做减法**。

-   **实战流程：** 你的 Go 后端需要每隔一段时间去链上打个“快照”，把当前的累积价格存进数据库。**然后**当需要报价时，再从数据库里拿老数据跟当前链上数据对比算平均值。
    
-   **意义：** 这样就算黑客能在 1 秒内操纵价格，**但是**他无法改变过去 10 分钟的累积均值。均值就像一个稳重的长者，不会被瞬时的波动带偏。
    

* * *

### 📝 笔记心得：

之前觉得价格就是一个实时变动的数字，**然后**研究了 Uniswap 的预言机机制**才**明白，在区块链这种极度不安全的环境里，**“快”往往意味着“容易被骗”。**

作为后端开发者，我要理解 **“时间加权”** 的重要性：

-   **实时价（Spot Price）：** 适合高频交易，但容易被操纵。
    
-   **均价（TWAP）：** 适合结算、清算和风控。
    

**只有**学会了如何通过 Go 后端去存储和处理这些累积数据，**才**能为交易所搭建一套抗操纵的价格预警系统。**否则**，一旦遇到大额闪电贷攻击，后端系统**就**会因为盲目信任瞬时价格而导致严重的业务逻辑错误。

### 📘 知识点：Event Logs 与 布隆过滤器 (Bloom Filter) —— 链上数据的“搜索引擎”

**1\. 困境：大海捞针**  
以太坊现在的区块高度已经超过 1900 万。假设你的 Go 程序要监听“USDT 的转账事件”，如果让节点把每个区块里的每笔交易都解包看一遍，那 CPU 和 IO 会直接爆炸。

**那节点是怎么做到毫秒级响应 eth\_getLogs 请求的？**  
答案是：**布隆过滤器 (Bloom Filter)**。

**2\. 核心机制拆解**

当你写下这行 Solidity 代码时：

code Solidity

downloadcontent\_copy

expand\_less

```
event Transfer(address indexed from, address indexed to, uint256 value);
emit Transfer(A, B, 100);
```

底层发生了三件事：

-   **Topics (索引区)：**
    
    -   Topic\[0\]: 事件签名的哈希（即 keccak256("Transfer(address,address,uint256)")）。
        
    -   Topic\[1\]: from 的地址（因为加了 indexed）。
        
    -   Topic\[2\]: to 的地址（因为加了 indexed）。
        
    -   **特点：** 这些数据会被加入到区块头的 **Bloom Filter** 中。
        
-   **Data (数据区)：**
    
    -   value: 100。
        
    -   **特点：** 没加 indexed 的参数存这里。**它很便宜，但无法被直接检索**，只能等找到这条 Log 后再解码查看。
        
-   **Bloom Filter (快速筛选)：**
    
    -   每个区块头（Block Header）里都有一个 logsBloom 字段（256字节）。
        
    -   它是一个**概率型数据结构**。
        
    -   **原理：** 当你的 Go 程序问节点：“这个区块里有‘A 转给 B’的事件吗？”
        
    -   **回答：**
        
        -   如果 Bloom 说 **“没有”**：那 **100% 绝对没有**，直接跳过这个区块（不用读磁盘，极快）。
            
        -   如果 Bloom 说 **“可能有”**：那 **大概率有**，但也可能是误报（False Positive），这时候才需要去磁盘里读具体的 Log 验证。
            

**3\. 对 Go 后端开发的启示**

作为后端，你在写监听程序（Indexer）时，必须懂这个原理，才能写出高性能代码：

1.  **indexed 很贵但很关键：**  
    如果你想按“订单号”查询事件，一定要在 Solidity 里给订单号加 indexed。否则你的 Go 程序就得把全网数据拉下来自己遍历，慢到不可接受。
    
    -   _注意：_ indexed 参数最多只能有 3 个。
        
2.  **Topic 0 的陷阱：**  
    匿名事件（anonymous）没有 Topic 0，这会导致有些通用的监听器扫不到它。
    
3.  **精准查询 vs 范围查询：**  
    因为 Bloom Filter 只能告诉你“可能有”，所以如果你查询的条件太宽泛（比如只查 Topic 0），节点需要从磁盘加载大量数据来二次确认，这会拖慢 RPC 响应速度。**给 Filter 传的参数越精确，Go 后端的同步速度就越快。**

### 📘 知识点：ECDSA 签名与 ecrecover —— “不花钱也能证明你是你”

**1\. 场景引入：OpenSea 挂单为什么不花 Gas？**  
你在 OpenSea 上卖 NFT，点击“上架”的时候，只需要在钱包点一下“签名”，不用付 Gas 费，这是为什么？

-   **传统逻辑：** 你发一笔交易告诉合约“我要卖”，这需要 Gas。
    
-   **签名逻辑：** 你在链下（Off-chain）签了一张“条子”，上面写着“我同意卖”。这张条子只是一串加密数据，没上链，所以**免费**。等有人来买的时候，买家把这张“条子”带上链，合约验证条子是你签的，交易成交。
    

**2\. 核心原理：椭圆曲线数字签名 (ECDSA)**  
这是区块链的基石。

-   **私钥 + 消息 => 签名** (由 Go 后端或前端钱包完成)
    
-   **消息 + 签名 => 恢复出公钥/地址** (由 Solidity 合约完成)
    

在 Solidity 中，有一个内置函数叫 **ecrecover**，它的作用就是：**“给我一个签名，我告诉你这是谁签的。”**

**3\. 代码实战 (Solidity 侧)**

code Solidity

downloadcontent\_copy

expand\_less

```
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract SignatureVerifier {
    
    // 验证函数
    // _hash: 签名的内容（比如“转账100块”）的哈希值
    // _signature: 用户签出来的乱码
    function verify(bytes32 _hash, bytes memory _signature) public pure returns (address) {
        // 1. 将签名拆解为 r, s, v 三个部分 (这是椭圆曲线数学参数)
        (bytes32 r, bytes32 s, uint8 v) = splitSignature(_signature);
        
        // 2. 核心函数 ecrecover
        // 它会返回：在这个 hash 上签名的那个人的地址
        address signer = ecrecover(_hash, v, r, s);
        
        return signer;
    }

    // 辅助函数：拆解签名 
    function splitSignature(bytes memory sig) public pure returns (bytes32 r, bytes32 s, uint8 v) {
        require(sig.length == 65, "Invalid signature length");
        assembly {
            // 读取内存中的前32字节给r
            r := mload(add(sig, 32))
            // 读取接下来的32字节给s
            s := mload(add(sig, 64))
            // 读取最后1字节给v
            v := byte(0, mload(add(sig, 96)))
        }
    }
}
```

**4\. 为什么对Go 后端很重要？**

以后你经常会遇到这种需求：

-   **“钱包登录”**：用户在前端签名，把签名发给你的 Go 后端。你的 **Go 代码** 需要验证这个签名是不是该地址签的（Go 语言的 crypto/ecdsa 包或者 go-ethereum/crypto 包就是干这个的）。验证通过，颁发 JWT Token。
    
-   **“白名单 Mint”**：你的 **Go 后端** 作为管理员，用私钥给用户签发一个“白名单凭证”。用户拿着这个凭证去合约 Mint。合约用 ecrecover 验证“这确实是官方后端签发的”，然后放行。
    

**5\. 安全大坑：重放攻击 (Replay Attack)**  
如果我签了一个“给 Bob 转 10 ETH”的条子。

-   **风险：** Bob 可以拿着这张条子，去合约调用 10 次 verify，把我的钱转走 10 次。因为签名本身是有效的。
    
-   **解决：** 必须在签名内容里加一个 **Nonce (随机数/计数器)**。
    
    -   第一次转账：签名内容 = “给Bob转10个, nonce=1”
        
    -   第二次转账：合约记录 nonce 1 已使用，Bob 再提交就会失败。

之前认为签名就是“交易确认”，现在才明白签名可以**脱离交易**单独存在。

-   **Go 后端** 可以用它来做鉴权（证明你是账号主人）。
    
-   **Solidity** 可以用它来做免 Gas 授权（Meta-transaction）或白名单验证。
    

ecrecover 是连接链下意图（Off-chain Intent）和链上执行（On-chain Execution）的魔法门。对于想做交易所或 Web3 基建的人来说，**玩转签名是必修课**。

### 📘 知识点：整数溢出与 0.8.x 的自动保护

**1\. 核心问题：0 减 1 等于几？**  
在普通的数学里，0 - 1 = -1。  
**但是！** 在 Solidity 中，我们常用的类型是 uint256（Unsigned Integer，无符号整数）。

-   “无符号”的意思是：它只能存**非负数**（0, 1, 2...），**不能存负数**。
    

**2\. 以前的噩梦 (Solidity < 0.8.0)**  
在旧版 Solidity 中，如果你尝试用 0 - 1，EVM 不会报错，而是会发生“下溢 (Underflow)”：

-   数字会“倒转”回最大值。
    
-   结果变成：115792089237316195423570985008687907853269984665640564039457584007913129639935 (2^256 - 1)。
    
-   **后果：** 黑客利用这一点，把余额 0 减成天文数字，瞬间变成亿万富翁。
    

**3\. 现在的机制 (Solidity >= 0.8.0)**  
你现在的代码写的是 pragma solidity ^0.8.13;。  
从 0.8.0 版本开始，Solidity 编译器**内置了自动检查**：

-   如果运算结果会导致溢出（比如 0 - 1 或 最大值 + 1），交易会**自动失败并回滚 (Revert)**。
    
-   报错信息通常是：Panic(0x11) (Arithmetic overflow/underflow)。
    

* * *

利用你现在的环境，你可以亲自验证这个保护机制：

2.  **尝试强行减 1 (触发报错)：**
    
    code Bash

你会发现终端里会报错，提示 Gas estimation failed 或者 execution reverted。这说明 Solidity 0.8 的保护机制生效了，它阻止了你把 0 变成负数，保护了你的合约。

**📝 笔记总结：**  
在 Solidity 0.8.0 之后，不再需要引入 SafeMath 库来防止溢出，编译器自带保护。任何导致 uint 变为负数的操作都会直接导致**交易回滚 (Revert)**。

### 📘 知识点：constant 与 immutable —— 变量里的“钉子户”

**1\. 背景：SSTORE 的痛**  
通常我们在合约开头定义的全局变量（状态变量），比如 address public owner;，它们是存在 **Storage** 里的。每次去读它（比如 owner == msg.sender），都要执行 SLOAD 操作，这虽然比写便宜，但也得花不少 Gas（暖读取 100 gas，冷读取 2100 gas）。

**那有没有办法不存 Storage，直接“硬编码”在代码里呢？** 有！

**2\. constant (常量)：出厂前就定死的**

-   **适用场景：** 你写代码的时候就已经确定的数值。
    
-   **例子：** uint256 public constant MAX\_SUPPLY = 10000;
    
-   **原理：** 编译器在编译的时候，直接把 MAX\_SUPPLY 替换成了数字 10000。它根本不占 Storage 槽位，而是变成了合约\*\*字节码（Bytecode）\*\*的一部分。
    
-   **读取代价：** 极低（接近于 0）。
    

**3\. immutable (不可变量)：出生时定死的**

-   **适用场景：** 写代码时不知道，但**部署那一瞬间**（在 constructor 里）确定后，这辈子就不再改的值。
    
-   **例子：** 你写的 Vendor 合约里的 YourToken 地址，或者 Owner 地址。
    
    code Solidity
    
    downloadcontent\_copy
    
    expand\_less
    
    ```
    address public immutable i_token; // 习惯在变量名前加 i_
    address public immutable i_owner;
    
    constructor(address _token) {
        i_token = _token; // 只能在构造函数里赋值一次
        i_owner = msg.sender;
    }
    ```
    
-   **原理：** 这是一个非常聪明的机制。合约部署时，EVM 会把构造函数里算好的值，直接**填空**填进合约的字节码里保存起来。以后读取它，也不需要去 Storage 查，直接从代码里读。
    
-   **读取代价：** 同样极低。
    

* * *

### 📝 笔记心得：

以前我写合约，不管是死数还是活数，通通只写个类型（如 uint256）。  
**然后**学了这个才明白，这就像是在建房子：

1.  **普通变量 (Storage)：** 就像家里的**家具**，以后随时能搬动，但占地方，搬一次很累。
    
2.  **constant**：就像是**地基里的钢筋**，盖房图纸上就画好了，永远动不了，也不占室内空间。
    
3.  **immutable**：就像是**装修时的定制柜子**，房子盖好（部署）的那一刻装上去，之后也就焊死动不了了，但也不占活动空间。
    

**最佳实践：**  
以后写合约，只要这个变量赋值之后**再也不会变**（比如代币总供应量、初始管理员地址、税率上限），**一定要**加上 constant 或 immutable。  
这不仅是为了省那一两千的 Gas，更是为了告诉读代码的人：“放心，这个参数是锁死的，项目方也没法偷偷改。”

### 📘 知识点：unchecked 代码块与溢出检查

**1\. 背景：SafeMath 的消亡**  
在 Solidity 0.8.0 之前（如 0.6.x, 0.7.x），整数溢出（Overflow/Underflow）是巨大的安全隐患。

_例子：_ uint8 最大是 255，如果你算 255 + 1，它会“回绕”变成 0。

_旧方案：_ 开发者必须引用 SafeMath 库来防止这种情况。

**2\. 现状：0.8.x 的内置保护**  
从 Solidity 0.8.0 开始，编译器**内置**了溢出检查。

_机制：_ 每做一次加减乘除，EVM 都会自动检查结果是否越界。如果越界，交易自动 **Revert**（回滚）。

_代价：_ 这种自动检查需要消耗额外的 Gas。

**3\. 进阶技巧：使用 unchecked 省钱**  
有时候，作为开发者，我们在逻辑上能 **100% 确定** 某个运算绝对不会溢出，但编译器不知道。为了省下那笔“检查费”，我们可以手动关闭这个保护。

**最经典的应用场景：for 循环中的 i++**

code Solidity

downloadcontent\_copy

expand\_less

```
//  普通写法 (Gas 稍贵)
// 编译器每次执行 i++ 都会检查：i 加 1 后会不会超过 2^256？
// 虽然我们知道数组长度根本不可能达到 2^256，但编译器不知道。
for (uint i = 0; i < array.length; i++) {
    // do something
}

//  优化写法 (Gas 便宜)
// 只要 array.length 不超过 uint256 上限，i 就不可能溢出。
for (uint i = 0; i < array.length;) {
    // do something
    
    // 告诉编译器：“这行代码不需要检查溢出，出了事我负责。”
    unchecked { i++; }
}
```

**📝 笔记核心：**

**安全性：** Solidity 0.8+ 默认安全，不再需要 SafeMath。

**Gas 权衡：** 安全是有代价的（Gas）。

**最佳实践：** 只有在**逻辑上绝对不可能溢出**的情况下（例如计数器受限于数组长度，或减法中已确认 a > b），才使用 unchecked { ... } 包裹运算代码，以此来榨取极致的 Gas 优化。不要滥用，否则会引入安全漏洞。

### 📘 知识点：tx.origin 与 msg.sender 的致命区别

你在写代码的时候，可能觉得 tx.origin 和 msg.sender 差不多，都是“谁在调我”。  
**但是！**这两者的区别就是“漏洞”。

**1\. 区别在哪里？**  
假设调用链是：**用户(A) -> 恶意合约(B) -> 你的银行合约(C)**

-   **msg.sender (直接调用者)：**
    
    -   站在 C 的角度看，直接敲门的人是 **B**。
        
    -   _比喻：_ 谁在敲门。
        
-   **tx.origin (交易发起者)：**
    
    -   站在 C 的角度看，最初发起这笔交易的人是 **A**。
        
    -   _比喻：_ 谁付的邮费。
        

**2\. 漏洞：钓鱼攻击 (Phishing)**  
如果你在合约里这样写权限控制：

code Solidity

downloadcontent\_copy

expand\_less

```
//  错误写法：只认“交易发起人”
require(tx.origin == owner, "Only owner can withdraw");
```

**黑客怎么攻击？**

1.  黑客做一个伪装成“领取空投”的恶意网站（背后的合约是 B）。
    
2.  你（A，也就是 Owner）被骗了，去点了那个网站的按钮（调用了 B）。
    
3.  B 在代码里偷偷调用你的银行合约 C 的 withdraw。
    
4.  **关键时刻：** C 检查 tx.origin。虽然是 B 在调 C，但**源头确实是你 A 发起的交易**。
    
5.  **结果：** 条件通过，C 以为是你本人在操作，于是把钱转给了黑客。
    

**3\. 正确做法**  
**永远只用 msg.sender 做权限检查。**

code Solidity

downloadcontent\_copy

expand\_less

```
//  正确写法：只认“直接敲门人”
require(msg.sender == owner, "Only owner can withdraw");
```

如果是这样写，上面那个攻击就失效了。因为 C 看到 msg.sender 是恶意合约 B，而不是 Owner 的钱包地址，直接拒绝。

### 📝 智能合约笔记：YourCollectible.sol

1.  **Web3 交互：** 我们不仅可以通过网页按钮（前端）跟区块链交互，还可以直接在控制台使用 JavaScript（通过 Web3.js 或 Ethers.js 库）直接调用合约函数。
    
2.  **Await 的作用：** 区块链的交互都是**异步**的（需要等待节点响应），所以在控制台调试时，使用 await 关键词可以让我们直接看到返回结果，而不是一个未完成的 Promise 对象。
    
3.  **合约是透明的：** 只要没有设置权限限制，我们可以读取合约里的任何 public 变量（比如这里的 password），这也提醒我们在开发时，**绝对不能把真的机密数据直接存在链上**，因为谁都能查到。
    

**Fallback 与 Receive 函数**  
这一关教的是合约如何处理“不请自来”的转账。

1.  **receive() external payable**: 当有人单纯往合约里转账（不调用任何函数，calldata 为空）时，如果合约写了这个函数，就会自动运行这里面的代码。
    
2.  **漏洞原理：** 很多合约会在 receive 里写一些逻辑（比如记录谁转了钱）。但如果像本关一样，把“修改权限”的逻辑写在了 receive 里，攻击者只需要转一笔小钱，就能触发这个后门，窃取权限。
    

**构造函数命名事故 (Constructor Naming Vulnerability)**

这是 Solidity 早期版本的一个重大设计缺陷。

-   **原理：** 在 Solidity 0.4.22 之前，构造函数必须和合约同名。如果开发者手误（比如 Fallout 写成了 Fal1out），编译器不会报错，而是把它当成一个普通的公开函数。
    
-   **后果：** 任何人都可以调用这个函数，重新执行初始化逻辑（比如窃取 Owner 权限）。
    
-   **修复：** 现在的 Solidity 强制使用 constructor 关键字，彻底杜绝了这种“手滑”导致的惨案。
    

**历史趣闻：** 这一关致敬的是 **Rubixi** 智能合约事件，当时开发者把合约名 Rubixi 的构造函数错写成了 DynamicPyramid（因为改了文件名忘了改函数名），结果任何人都能进去把钱提走。

### 📘 知识点：为什么卖币要签两次字？(Approve & TransferFrom)

**1\. 现象：**  
在 Uniswap 或 OpenSea 交易时，第一次操作某种代币（比如 USDT），系统总是强制让我先发一笔叫 **Approve** 的交易。等这笔交易确认了，然后按钮才会变成 Swap/Sell，这时候再发第二笔交易才能把币卖掉。

**2\. 核心逻辑：我的钱，合约不能随便拿**  
ERC20 标准：

-   **我自己**转账给别人：调用 transfer，想转就转。
    
-   **别人（智能合约）** 想拿我的钱：它没有权限直接扣款。
    

只有我先调用 approve 函数，在代币合约的账本上写下一笔：“我允许 Uniswap 动用我 100 个币”，才算完成了授权（Allowance）。  
接着，Uniswap 的合约再去调用 transferFrom，拿着我的授权记录去把钱划走。

**3\. 安全警示：无限授权 (Infinite Approval)**  
为了省去每次都要 Approve 的 Gas 费，很多 DApp 会默认让我授权“无限额度”（比如 11579...一长串数字）。

-   **风险：** 这相当于给了对方一张无限透支的信用卡。
    
-   **后果：** 万一这个 DApp 的合约有后门或者被黑了，黑客不需要我的私钥，直接凭着这个无限授权，就能把我的 USDT 全部转空。
    
-   **对策：** 用完不知名的小项目后，一定要去 [**Revoke.cash**](http://Revoke.cash) 这种工具把授权取消掉，才算真正安全。

### **知识点：require 函数与“时光倒流” (Revert)**

**1\. 合约里的“保安”：**  
你会在代码最前面写一句类似这样的话：

code Solidity

downloadcontent\_copy

expand\_less

```
require(msg.value >= 0.1 ether, "Not enough money!");
```

这行代码的意思就是：保安站在门口查票，**只有**你付的钱大于等于 0.1 ETH，**才**让你进门继续执行后面的代码；**如果**没给够，直接把你拦回去，并冲你喊一句 "Not enough money!"。

**2\. 核心特性：时光倒流 (Revert)**  
这是区块链最神奇的地方。  
假设你的函数里有 3 步操作：

-   第一步：修改了一个数据（比如计数器 +1）。
    
-   第二步：做了一些计算。
    
-   第三步：碰到了 require，而且**条件不满足**（报错了）。
    

**这时候会发生什么？**  
它不仅仅是停止运行，而是会触发 **Revert（回滚）**。  
也就是说，**之前第一步里做出的修改（计数器 +1）会全部作废，就像时光倒流一样，恢复到交易发生之前的状态。**

**📝 笔记总结：**  
在 Web2 写代码（比如 Python），程序报错可能只是一半没跑完，前面的数据已经改了。  
但在 Web3（Solidity），交易具有**原子性（Atomicity）**。**require** 不仅是做判断的，更是用来保命的——**只要**最后一步没跑通，**那么**整个过程就像没发生过一样，这样**才**能保证账本永远不会乱。

### **知识点：Metadata (元数据) 与 JSON 标准**

在做 Simple NFT 的时候，你可能注意到代码里并没有地方让你上传 JPG 图片，只有一个叫 TokenURI 的东西。这背后的逻辑是 Web3 开发必须懂的“潜规则”。

**1\. 链上只存“路标” (Pointer)**  
由于在以太坊上存 1MB 的数据可能要花几万美金（Gas 费），所以我们**绝对不会**把图片直接存进合约里。

-   **合约里存什么？** 只存一个字符串链接，叫 tokenURI。
    
-   **例子：** ipfs://QmYourHash.../1.json
    

**2\. 链下才存“真身” (JSON)**  
当你把这个链接放到浏览器里打开，你会发现它不是图片，而是一个**文本文件（JSON 格式）**。这才是 NFT 的本体。  
标准的 **ERC721 Metadata** 格式长这样：

code JSON

downloadcontent\_copy

expand\_less

```
{
  "name": "My Simple NFT #1",
  "description": "这是我在 SpeedRunEthereum 做的第一个 NFT",
  "image": "ipfs://QmImageHash.../1.png",  // 这里才指向真正的图片
  "attributes": [ ... ]
}
```

**3\. 谁在读这个文件？**  
你的合约其实并不关心图片长啥样。是 **OpenSea、MetaMask** 这些前端应用，它们会：

1.  去链上读你的 tokenURI。
    
2.  顺着链接去下载那个 JSON 文件。
    
3.  解析 JSON 里的 "image" 字段，把图片展示给用户看。
    

**📝 笔记总结：**  
NFT 的合约只是个“收据”，而 Metadata（那个 JSON 文件）才是“商品说明书”。**开发 NFT 不仅仅是写 Solidity，更重要的是要懂得如何生成和托管这个标准的 JSON 文件**，否则你的 NFT 在 OpenSea 上就是一张裂开的图。

### 知识点：Events (事件) —— 链上最便宜的“广播系统”

**1\. 核心机制：链上发声，链下听**

-   **代码行为：** 在 ERC721 标准里，每次转账或铸造，最后都会有一行代码：emit Transfer(from, to, tokenId);
    
-   **比喻：** 智能合约就像一个关在黑屋子里的机器人。修改变量（State Variable）是它在屋里写日记，外面人看不见（除非主动敲门去查）。但 emit Event 就像是机器人往窗外放了一只**信鸽**，告诉全世界：“刚刚发生了这件事！”
    

**2\. 为什么不用变量存数据？（Gas 费刺客）**

-   **省钱大法：** 在以太坊上存数据（SSTORE）极贵。如果你想记录“谁在什么时间 Mint 了什么”作为历史记录：
    
    -   **用数组存：** 贵到破产。
        
    -   **用 Event 存：** 非常便宜（Gas 费通常只有存储变量的 1/10 甚至更低）。
        
-   **代价：** Event 存的数据是\*\*“只写”\*\*的。智能合约自己读不到自己以前发的 Event（机器人放飞了信鸽，它自己就抓不回来了）。
    

**3\. 实战意义：Indexed (索引) 的魔力**  
在代码里，你常看到 event Transfer(address indexed from, ...)。

-   **Indexed 关键词：** 加了这个词，就相当于给信鸽绑了个**特定颜色的丝带**。
    
-   **作用：** 前端或后端（如 The Graph）可以极快地过滤出相关信息。比如：“只监听所有 from = 我 的事件”。如果没有 indexed，前端就得把全网的信鸽抓下来一只只看信的内容，效率极低。
    

* * *

**一句话总结：**  
**Events (事件)** 是连接区块链“黑盒”与 Web 前端“界面”的低成本通信协议。它是给**人**（和前端程序）看的，不是给**合约**看的。以后设计合约时，如果数据不需要被合约逻辑再次使用，只为了留痕展示，**永远优先用 Event，别用变量存。**

关于 **ERC721 数据存储逻辑与 Gas 权衡** 的深度知识点笔记

### 知识点：ERC721 的“单向映射”与 Enumerable 的代价

**1\. 核心矛盾：Mapping 的“失明”**

-   **现象：** 在标准的 ERC721 代码中，核心数据结构是 mapping(uint256 => address)。
    
-   **本质：** 这是一种**单向查找**机制。
    
    -   **能做：** 拿着 TokenID 查主人（比如：查 #100 号是谁的）。
        
    -   **不能做：** 拿着主人查 TokenID（比如：查 Alice 名下所有的 NFT）。
        
-   **原因：** Solidity 中的 Mapping 就像一个没有目录的巨大仓库，它不记录“列表”。如果要强制查询某人名下的所有币，链上必须遍历所有 ID，这会导致 Gas 费爆炸甚至超出区块上限。
    

**2\. 解决方案：ERC721Enumerable**

-   **定义：** 这是一个官方扩展标准，它额外增加了数组（Array）来记录 Token 的索引。
    
-   **功能：** 开启后，合约可以轻松返回 tokenOfOwnerByIndex，让前端直接读取用户的 NFT 列表。
    

**3\. 关键权衡 (The Trade-off)**  
这是新手进阶必须理解的“守恒定律”：**查询越方便，写入越昂贵。**

-   **使用 Enumerable：** 读取数据很爽，但在执行 mint 或 transfer 时，合约需要同时修改 Mapping 和 Array，导致 **Gas 费大幅上升**（可能贵 30%-50%）。
    
-   **不使用 Enumerable：** 写入操作（Mint/转账）很便宜，但前端无法直接问合约要列表。
    
    -   _替代方案：_ 依赖链下索引工具（如 **The Graph** 或 Alchemy API）来帮用户整理数据，而不是把数据“死记”在链上。
        

* * *

**总结：**  
区块链不仅是存数据的，更是**计费**的。在写合约时，如果不是必须在链上遍历数据，尽量不要用 Enumerable，把复杂的查询压力甩给链下（Off-chain），把最贵的链上资源留给核心逻辑，这才是“省 Gas”的高级心法。
