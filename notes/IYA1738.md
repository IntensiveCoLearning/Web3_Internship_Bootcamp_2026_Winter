# 2026-02-04
<!-- DAILY_CHECKIN_2026-02-04_START -->
用 Rust 把 MEV 场景下的交易回测又推了一轮，整理下来发现，很多看起来只是“写个小模拟器”的地方，其实在工程上已经非常接近一个缩小版的策略引擎。最先踩到的是“结构建模”这块：一开始只是随便写了个 Trade { id, pair, amount\_in, amount\_out, gas\_cost, success } 做单笔模拟，但当我引入路径、跳数、不同池子组合之后，Trade 只是叶子节点，真正有意义的是 Path / Route / DaySummary 这些更高层级的 struct。如果一开始结构建模就只停留在“把数据堆在一个 Vec 里”，后面一旦想对路径做聚合统计（比如按 pair 分组、按策略标签分组），整个代码会立刻变得非常难维护。Rust 的 struct + impl 强迫我在一开始就把“这个对象的语义是什么，它拥有什么行为”讲清楚，这一点对于 MEV 这种充满状态和约束的系统特别重要。

另一个明显感受到的坑在于数值精度和 f64 的使用。简单的模拟里用 f64 做 amount、profit、gas 看起来没问题，但一旦做大量路径乘积（多跳汇率、复利累计、长期回测）时，浮点误差会在几千、几万次迭代后出现肉眼可见的偏移——尤其在“是否盈利 > 0”这种二分类条件下，误差足以直接改变某条路径的胜负判定。现实中链上是以整数 wei 计价，而回测引擎里如果偷懒用浮点，最后得到的盈亏统计是“近似正确但边缘极不可信”的。更合理的做法其实是把链上的整数金额原样建模成 u128 或定点数，然后只在展示层做格式化，这和 Rust 的类型系统是契合的：用类型来表达“这里严禁出现非精确计算”。

在路径搜索这块，今天把 Dijkstra 改成了“最大输出版本”之后，直观感受到 Rust 把算法和状态管理绑在一起的那种安全感：best\[u\] 表示当前能在某个 token 上拿到的最大金额，prev\[u\] 记录路径前驱，配合 Option 把“路径的存在性”和“路径的终止条件”编码进类型里。相比过去在脚本语言里随便写个 dict 拼路径，Rust 这种写法虽然啰嗦，但不会出现“某个节点 prev 没初始化”“路径回溯到一半崩掉”这种 silent bug。更有意思的是，一旦把这个搜索器接到 MEV 回测上，比如“在某个时间段内，针对同一撮合池尝试多种路径并记录最优出币量”，这个 Dijkstra 实现几乎可以零改动地复用，只要换一下 Edge 的含义（汇率函数/滑点模型）就行。

随机模拟这块也暴露出一个很现实的问题：为了生成一堆“看起来合理”的策略样本，我用 rand 随机生成交易对、输入金额、成功率、净利润等参数，然后做 Monte Carlo 式的聚合。Rust 在这里的优势是把“生成过程”和“评估过程”拆得极干净：一个函数专门生成 Vec<Trade>，另一个函数只管对 &\[Trade\] 做统计。这样做的好处是非常利于后面换数据源——今天用随机，明天可以直接把链上真实 mempool / block 数据 decode 成 Trade / Path 结构，整个分析逻辑不用大改，只是把“数据输入层”换成真实世界。相比之下，如果一开始就把随机生成、状态更新、统计输出全部写死在 main 里，后面想接链上真实数据几乎等于重写。

# 2026-02-03
<!-- DAILY_CHECKIN_2026-02-03_START -->

今天重新过了一遍 Rust 在图算法与基础语义上的边界表现，在真实工程场景下影响极大的关键细节。首先注意到 `vec![x; n]` 在二维容器初始化时的隐性 clone 语义：此写法并不是生成 n 份独立的容器，而是对同一个元素做 n 次 clone，因此内部类型一旦未实现 Clone（例如 `Vec<Edge>` 中的 `Edge` 未派生 Clone），初始化阶段就会直接编译失败。这种隐式 clone 行为在 Rust 文档中从不强调，却会在书写多维图结构的邻接表时反复踩雷；最稳妥的方式反而是用迭代器 `(0..n).map(|_| Vec::new()).collect()` 主动生成 n 个独立节点，避免 clone 语义干扰建图逻辑。

另一个今天重点验证的点是 Option 的语义边界，远比“可空值”更深。Option 不是用来替代 null，而是 Rust 强制构建安全状态机的原语：例如在 Dijkstra 的路径回溯中，`prev[src] = None` 实际承担了“状态终点”的角色，而 `Some(u)` 则形成“可追溯链条”。这意味着 Rust 在语义层面直接禁止“野指针”或“无前驱节点”的非法访问路径，大幅提升了搜索器的安全性。路径回溯时 `while let Some(p) = prev[current]` 这种写法几乎不可能出错，比其他语言那种“判 null + 自己维护边界条件”的方式健壮数倍。

又一个容易被忽略的特性是：Dijkstra 从不对“边”贪心，而是对“节点状态”做贪心。也就是说，正确的写法永远是维护一个 `best[u]` 作为“到达节点 u 时能获得的最佳价值”，每轮选择 best 最大的未确定节点，而不是在所有可访问边里选倍率最大的那条边。后者在路径搜索器、MEV 模拟器中是极常见的误区，会导致局部最优路径抢先被选中、从而遗漏真正的全局最大乘积路径。在 Rust 重写一遍后，这个节点驱动的贪心逻辑变得非常清晰：`best[u]` 是状态，边只是状态转移工具。

今天还注意到 Rust 的 ownership 模型在图算法中有独特的表现：若函数以 `Graph` 按值接收，就会直接 move 掉整个图结构，后续无法继续访问，打印 token 名称时就会触发“borrow of moved value”错误。唯一正确的方式是整个路径搜索函数都使用 `&Graph`，严格区分“谁持有所有权、谁只是临时借用”。在复杂路由器、订单簿模拟器、MEV 机会扫描器中，这种 ownership 精确性可以显著减少悬挂引用、状态错配等隐性逻辑缺陷

# 2026-02-02
<!-- DAILY_CHECKIN_2026-02-02_START -->


今天重新翻了一些 EVM 的边界表现，整理了几条在合约开发和审计中很少有人真正提到，但现实中却有巨大影响的冷门知识。首先注意到 CALL/DELEGATECALL 的 gas 行为在某些极端情况下会触发“隐形 gas cap”：也就是说，虽然在 Solidity 层面传入了固定 gas，但当被调合约非常大、或者当前调用深度接近 1024 层时，EVM 会强制加上一个动态 cap，从而导致被调函数在内部执行到一半突然 OOG。这在多层嵌套合约、尤其是复杂代理链下非常容易触发。此行为不会在 Solidity 文档里出现，但会在高复杂度协议中出现难以解释的 partial execution failure，要避免只能控制调用深度与执行分支复杂度。

另一个今天特意验证的点是：EVM 对“内存页扩容”的收费具有非线性跳跃特征。绝大多数开发者只知道 memory 扩容会按 (newSize² - oldSize²) 计费，但更冷门的是，当进行一次小规模 mstore 却越过某个分界点（例如跨过 0x1fff、0x3fff 等边界），内存页的平方成本会突然跳升，导致一个看似无关紧要的数组拷贝突然变贵几十倍。这意味着——动态数组 push/构建大型 bytes 时，边界位置非常关键，甚至能反过来影响函数分支，属于 compiler 层级难以察觉的问题。

另一个十分奇怪的行为是 revert data 的“静默截断”：当被调合约返回极长的 revert string 时，虽然全节点会保留完整 revert data，但 L2 节点（特别是某些 rollup）会对返回数据做 silent truncate，这意味着某些协议依赖 revert data 来分辨错误类型时，会因为链的差异性在 L1 与 L2 得到不一致结果。更坑的是，这种 truncate 不会报错，只是 silently fail，导致 debug 极难。很多跨链桥协议曾因此埋下逻辑分叉风险。

今天还验证了一个更隐蔽的特性：EVM 不会对“写入同一 storage slot 的连续 SSTORE”做任何优化，但如果采用 assembly，将同一 slot 写入值 0 → 非零 → 0 时，某些编译器版本会生成错误的 refund 逻辑，导致 gas refund 无法按预期领取。这属于“编译器 bug + EVM refund edge case”的组合，通常只在复杂清算协议、拍卖协议和 AMM 设计中才会被触发。工程上最安全的策略是避免对同一 slot 在一次执行路径中做三次以上的反复写入

最后一个观察来自 CREATE2：很多人知道 CREATE2 地址可预测，但很少有人意识到——如果部署字节码中包含某些特殊常量（特别是大整数常量），编译器在 optimizer 模式下会尝试“常量折叠”，导致最终 bytecode 的局部变化，从而引起 CREATE2 地址偏移。也就是说，把一个 uint256 常量从 1 改成 2，理论上不会影响逻辑，但可能改变最终部署地址。这对某些 factory 架构来说是灾难性的，因为地址是协议状态的一部分，而开发者自己却可能没有意识到优化器已经改变了 bytecode。解决途径通常是禁用优化器或在 factory 中使用 bytecodeHash，而非直接编码 bytecode。

# 2026-02-01
<!-- DAILY_CHECKIN_2026-02-01_START -->



今天继续深挖了一些 Solidity 和 EVM 的冷门行为，主要集中在调用路径、存储稀疏化以及 ABI 编码的灰色区域。首先注意到 external 调用在 EVM 层面其实分成三个阶段：selector 匹配、参数解码、fallback 分支，而其中 selector 匹配失败并不会立即进入 fallback，而是会先看 calldata 长度是否足够解码所有参数。也就是说，一个 external 函数如果 selector 被撞到，但 calldata 不够长，则会直接 revert，而并非 fallback，这在某些 delegatecall 链路里可能导致意外回滚。再加上 selector 空间本身只有 2³²，链上合约数量巨大，selector 偶发碰撞的概率并不忽略，尤其在 proxy 架构中更需要意识到这一点。

另一个比较隐蔽的点是 EVM 对 storage 的“稀疏写入”策略：SSTORE 操作只对 32 字节 slot 生效，而变量间的“空洞”永远不会被清零。利用这个特性，可以通过刻意设计 struct 中的 unused 区域，把某些非关键数据丢到 padding 区，减少显式 SSTORE 次数，从而节省 gas。反过来说，如果攻击者掌握 struct 的 layout，也能利用 padding 区域进行“伪存储覆盖”，所以 struct 的布局不是完全安全的抽象，必须明确整理。很多人以为 storage 是连续的，其实底层完全依赖 slot hash，因此“伪连续”只是语言层的幻想。

再一个非常少见但极有用的技巧是利用 ABI 的“自动紧缩”特性：当传递静态数组或固定长度 bytes 时，ABI 编码会直接执行按值写入，而不会分配 offset，意味着可以利用这一点做极低成本的 in-place 参数拼接，而不用走动态数组那套昂贵的 offset–length–data 结构。这使得某些批量操作函数可以完全避免动态数组，显著降低 ABI 编码成本，并且更利于 calldata 拼装，尤其适合链上 Merkle proof 拼接等高性能场景。

最后一个今天才意识到的冷门细节是：当使用 staticcall 调用返回值超过 0x6000 字节的数据时，EVM 会直接截断返回值，而不是报错。也就是说，被调合约实际返回的数据比看到的更多，只是调用方 buffer 不够大，这会造成某些 “返回数组为空但实际上不是空” 的假象，尤其在链上做大规模编码或尝试检索大结构体时。解决方式是手动预估 max return size 或使用 assembly 扩大 return buffer，这种异常在普通 dapp 项目里几乎不会遇到，但在 protocol 级设计、indexer 调用链上合约、或利用 create/destroy 合约做数据搬运时很容易踩到。

# 2026-01-31
<!-- DAILY_CHECKIN_2026-01-31_START -->




今天继续研究 Solidity 的底层特性，重点整理了几个平时极少有人讨论、但在工程化开发与审计中非常有价值的冷门技巧。首先是 calldata 的“隐含参数”机制，EVM 并不会检查开发者声明的参数数量，因此只要外部调用在 calldata 尾端追加额外字节，被调用合约就能用 calldataload 直接读取这些隐藏信息。这也是 meta-tx 身份错位问题的根源，在 forwarder、delegatecall 组合调用中尤其要注意。另一个很容易被忽略的点是 memory 的天然 zero-fill —— EVM 在扩容 memory 时总是返回全零区域，因此创建动态数组、结构体时无需手动初始化，减少 gas 的同时还能避免不必要的循环开销。

在做底层数据重排时还可以利用“反向 copy”来规避 memmove 覆盖问题：如果源与目标区间有重叠，从尾部向前拷贝可以完全避免破坏源数据，这在处理 ABI packed 数据、变长数组拼接时是非常实用的小技巧。此外，extcodesize(addr) 返回 0 并不能证明对方是 EOA，因为合约在构造阶段、合约被自毁后、以及 CREATE2 预留地址的情况下同样会返回 0，不可靠的 EOA 判断本身就是一个伪命题。最后一个很隐蔽的优化是条件反转带来的 JUMPDEST 减少：在某些分支结构中，把条件写成反逻辑，让“不执行”的路径成为 fall-through，可以减少一次 JUMPDEST，从而降低几十 gas，属于只有深入研究编译器 IR 才会注意到的细节。

# 2026-01-30
<!-- DAILY_CHECKIN_2026-01-30_START -->





今天在研究 calldata 解码的底层机制时，终于把高层 abi.decode 和底层 calldatacopy/calldataload 之间的关系彻底吃透了。以前只是模糊知道“手写 assembly 会更省 gas”，但今天是第一次把 ABI 编码的真实布局、EVM 访问模型、memory 扩容机制三者一起串起来，形成了清晰的 mental model。

最大收获就是理解到：abi.decode 并不是简单的“从 calldata 取东西”，它会自动帮你跑一整套通用解码逻辑——偏移定位、动态参数跳转、长度验证、内存拷贝、ABI 结构完整性检查等等；所以 bytecode 会非常臃肿。而在 assembly 里，你如果完全知道参数的 ABI 编码布局（尤其是纯 static 类型时），可以直接通过 calldataload(offset) 把参数从 calldata 原样读到栈上，甚至连内存都不需要，callgraph 里完全不存在复制、padding 和 boundary check。这种差异在高频路径里能省掉的 gas 是数量级的差别。

进一步的点是：calldatacopy 本质上只是“从 calldata 的 offset f 拷 s 字节到内存 offset t”，并不理解 ABI，只是纯字节搬运。所以当你知道多参数的 ABI 排布，例如 selector 占 4 字节、每个 static 参数各占 32 字节、dynamic 参数是 offset + length + data 区，就能在 Yul 中精准拼出内存布局，用 mload 在内存中随意访问这些参数，完全绕过通用 decode。这种从 calldata 到 memory 的“手动搬运”也让我第一次真切感受到 proxy 代码为什么用 calldatacopy(0, 0, calldatasize()) 原样转发：因为 data 已经是 ABI 完整结构，根本不用解码，只要复制整个 payload 再转发给 implementation 就行。

更进一步，也把“引用 calldata”与“复制到 memory”之间的边界理解清楚了：只有 bytes calldata 或 uint256\[\] calldata 属于零拷贝 sliced view，assembly 下的 calldataload 是直接栈读，而 calldatacopy 其实是显式复制。很多场景里根本不需要复制，尤其是 static 参数，直接 calldataload(4)、calldataload(36) 这种 offset 定位的方式，是 decode 的最低成本路径。

整体来说，今天的学习把我从“知道可以省 gas”升级到“知道为什么能省 gas、怎么省 gas、还能省到什么程度”。以后在写路由、聚合、batch call、meta-tx、proxy 这些高频逻辑时，我会优先考虑：能否直接用 calldataload 读出参数、能否跳过通用 ABI 解码、是否可以按字节拷贝、是否可以信任参数 layout、哪些部分能零拷贝、哪些必须搬到内存。这类底层掌握对 gas 优化的思考方式影响很大，也是今天最大的认知升级。

# 2026-01-29
<!-- DAILY_CHECKIN_2026-01-29_START -->






今天做基础技术任务里有一个Gas优化，把自己笔记中的gas优化看了看，然后再去研究了一些冷门的平常根本想不到的gas优化方法

首先是利用短路逻辑实现接近零成本的 revert，把传统的 require 或 if…revert 用 ok || revert(); 替换掉，可以省掉 error selector 和 ABI 编解码生成的字节，特别适合内部循环或 hot path。  
  
其次是 memory 本身在扩容时天然 zero-fill，所以在构造一些固定长度的 calldata/payload 时，不需要自己额外 mstore 去清零低位，直接覆盖高位即可，少一次 SLOAD/MLOAD 就是省一次。  
  
再来就是 mapping 的 slot 读写比数组成本高，如果访问模式是按顺序、遍历或固定长度访问，优先数组而不是 mapping，可以减少一次 keccak256。还有针对 external/internal 的选择，external 会自动生成 ABI 解码，对参数复杂的情况反而更省；而 internal call 是纯跳转，没有 ABI decoding，适合 hot path 内部逻辑。  
  
如果某个存储变量逻辑上永远是非零的，把它定义成 uint256 并用非零初始化，可避免之后所有相关逻辑出现零检查，并且还避免出现“零为默认值”导致的额外分支，长期累积能省不少 gas。

# 2026-01-28
<!-- DAILY_CHECKIN_2026-01-28_START -->







今天在做 damn vulnerable defi的naive-receiver 这题时，意外地又踩到了一个典型的 meta-transaction 身份错位问题。Pool 为了支持 forwarder，把 _msgSender() 改写成“如果是 forwarder 调用，就从 calldata 尾部取出 20 字节当成真实调用者”，但 forwarder 本身是完全开放的，任何人都能构造一笔 meta-tx。再加上 pool 又提供了一个 multicall，内部用的还是 delegatecall，整个调用链的身份层层“透传”，最终形成了一个非常容易被利用的权限绕过：你可以随意伪造任意地址作为_ msgSender()。

利用方式也很直接：先通过 flashLoan 的固定手续费把 receiver 的余额刷空，然后构造一笔通过 forwarder 进入 multicall，再进入 withdraw 的调用，把伪造的地址拼接在 calldata 最后。Pool 在 withdraw 时读取的“sender”就变成了你想冒充的地址，从而可以把池子里的全部 WETH 直接提到 recovery。

这个案例本质上不是“题目特制的 Trick”，而是实际项目里会频繁踩到的组合性风险：meta-tx、delegatecall、calldata 拼接和 \_msgSender() 重写放在一起时，如果缺乏严格的信任边界，调用者身份是很容易失真的。今天主要的收获就是再次确认：**只要合约允许别人通过 calldata 改写调用者身份，那它的权限体系基本等于不存在**。

# 2026-01-27
<!-- DAILY_CHECKIN_2026-01-27_START -->








今天把 staking 的整套逻辑从头到尾过了一遍，结果还是踩了不少细节，发现这类线性产出 + 按份额分配的模型，比看上去复杂不少。记录一下关键点，免得以后再掉坑里。

第一个明显的坑是 **accRewardPerShare 的语义必须保持一致**。一开始我把它当成“累计产出的总 reward”，越写越不对劲，直到意识到它应该始终代表“每 1 单位 stake 所能分摊到的累计奖励”。这个命名如果偏掉，后面的 settle、debt 对齐、pending 计算都会跟着混乱。

第二个点是 **epoch 的时间窗口必须强约束**。rewardDelta 的时间区间必须是 min(block.timestamp, endTime) - lastTimeUpdate，不能用裸的 block.timestamp。否则 epoch 结束以后还会继续产出奖励，accRewardPerShare 会扩到不合理的值，在线性奖励模型里这是实际违反经济语义的。

第三个常见错误是 **totalStaked == 0 时不能增长 accRewardPerShare**。没有 stake 就没有奖励，这是核心假设。如果忽略这个条件，会产生明显的套利：任何人可以在 epoch 后半段突然 stake 一次，把之前所有未分配的 reward 一次性吃掉。

第四个点是 **stake/unstake 的结算顺序必须严格正确**。

正确顺序应该是：

1.  \_update（更新池子状态）
    
2.  settle（基于旧仓位结算 pending）
    
3.  修改用户的 stakeAmount / totalStaked
    
4.  重算 rewardDebt 对齐
    

如果跳过 settle，或者在未对齐 debt 的情况下改变 stakeAmount，下次交互时会重复计算旧仓位的 reward，形成 double-count。

第五个点和状态结构有关：**多 epoch 必须把 UserInfo 做成二维 mapping**。

如果用户所有 epoch 共用一份数据，会发生交叉污染：在一个 epoch 的 stake 会影响另一个 epoch 的 rewardDebt 计算，导致整个奖励体系失真。

最后是小问题：**如果 epoch 从未 notify，reward 全部为 0，看起来像逻辑错了**。

今天前端连完之后怎么测都没有 pending，排查半天发现其实我根本没开 epoch。Staking 系统的开关状态必须明确，不然任何计算都不会动。

整体看下来，staking 系统的难点不在“公式”，而在一整套时序和状态机要完全一致。只要有一个变量在不该更新的时候更新，或一个窗口没裁好，奖励分配就容易出现套利空间或结算失真。

# 2026-01-26
<!-- DAILY_CHECKIN_2026-01-26_START -->









今天把整个 staking 模块从头跑了一遍，结果意外发现几个容易被忽略的小坑，记录一下免得以后再踩。

第一个问题是 accRewardPerShare 的语义一定要保持干净。它代表的是“单位质押量对应的累积奖励”，不是“这段时间产出了多少 token”。我最初的版本里把 rewardDelta 直接加进 acc，然后后面又除一次 totalStaked，相当于把两种概念混在一起。逻辑看起来没崩，但会计意义直接对不上，尤其在新用户进场和老用户持仓变化时，会出现不该被吃掉的奖励被吃掉、或者 rewardDebt 对不齐的情况。

第二个坑出现在 rewardDebt 的同步时机上。如果用户在 unstake 后 rewardDebt 不立即对齐，那下一次 settle 会用“旧的 rewardDebt × 新的 stakeAmount”进行计算。表现出来就是 pending 多算一段，纯粹因为变量不是同一时刻更新的。这个问题比较隐蔽，光看公式看不出来，一跑流程就明显出错。

第三个是时间边界。一开始没认真处理 endTime，导致 period 结束后奖励仍然在往外释放；没处理 totalStaked==0，又会出现没人质押但奖励曲线继续往前走的情况。单独看都能解释通，但组合在一起会让整个模型变得很奇怪。最后是 view 层，如果不在读取时模拟一次 update，前端看到的 pending 会一直落后真实状态半拍，看起来像奖励没在增长。

整体下来，staking 的难点倒不是公式，而是每个变量的语义必须严格对齐，更新顺序必须完全一致，否则只要有一处时间点不统一，整个奖励分配就会偏一段。今天算是把这些地方全都重新校了一遍，之后应该不会再踩了。

今天随手看了个合约的 _safeMint 扩展逻辑，结果又发现一个特别诡异的点：_beforeTokenTransfer 里做余额检查真的能把自己玩死。因为 ERC721 转账流程是 before → storage 更新 → after，有些人喜欢在 before 里做“限制当前余额”“限制当前 owner 状态”这种业务判断，结果一旦某些合约用 safeTransferFrom 搭配回调、或 batch mint、或 operator 代操作，before 看到的是“没更新前的状态”，以为这里能拦住异常状态，实际上组合起来会直接 bypass 判断。更阴间的是，如果在 before 里连 allowance／授权检查都自定义覆盖掉，那 operator 转移会出现“检查通过但实际 owner 还没更新”的奇怪过渡态，导致多次转移路径里出现 ghost owner，一眼看上去相当奇怪。总之，ERC721 的 before/after 钩子千万不能拿来当 “真实状态校验”，它处理的是“即将发生的动作”，不是“当前已发生的状态”，写过头了真的会把自己绕晕。

# 2026-01-24
<!-- DAILY_CHECKIN_2026-01-24_START -->











今天看了一下 ERC20 + Permit 的代币，结果发现这个东西也挺容易踩坑的，顺手记录一下今天遇到的几个点，免得以后再坑自己。

1.  Permit 的 nonce 管理非常容易写错。
    
    标准要求每次成功签名执行都必须自增 nonce，但实现上很容易在两个地方写成先读再存或者忘记自增，导致重放攻击风险。另外注意一点，nonces\[owner\]++ 必须在所有校验通过后执行，否则出现验证失败但 nonce 升了的诡异状态。
    
2.  Deadline 的逻辑不要写反。
    
    Permit 里的 require(block.timestamp <= deadline) 和 >= 很多人肉眼一飘就写错。
    
    一旦方向写反，permit 会直接永不过期或永远过期，这类 bug 提交到测试网根本不容易被人立刻发现，因为多数人不会测极限 timestamp。
    
3.  DOMAIN\_SEPARATOR 不能偷懒硬编码。
    
    在链上环境可能遇到 fork、chainId 变化（比如 L2 上特别明显），如果合约选择 lazy load 的 domain separator，就要把 chainId 缓存逻辑写正确。尤其是 EIP712 要求的计算方式，一旦 chainId 换了但合约没更新，会导致所有签名全部 invalid。
    
4.  owner == spender 的 permit 要特别处理。
    
    标准允许同一个地址给自己授权，逻辑上没问题，但实际实现时如果 allowance 写法不小心绕过了检查，可能导致 allowance 无限叠加。大多数实现不会出问题，但自写的时候确实容易忘记 owner==spender 的特殊性。
    

Permit 完成后 allowance 更新要注意两种情况。

需要区分：

1.  类似 USDC/DAI 的“覆盖式” allowance：permit 会直接将 allowance 设置为指定值。
    
2.  ERC20 的“追加式” allowance：写错很容易变成无限增加模式。
    
    一旦业务逻辑错了，后续 transferFrom 就会出现完全意料之外的结果
    

整体总结一下：Permit 看起来是个很基础的扩展，但里面细节多、变量多、分支多，且大部分 bug 都很隐蔽，写的时候一定要逐行确认规范，不然非常容易在一些以为不会出错的地方翻车一次。

# 2026-01-22
<!-- DAILY_CHECKIN_2026-01-22_START -->













今天看到做meta-transaction的gas relayer的forwarder合约中的这段代码

```solidity
if (gasLeft < request.gas / 63) {
            assembly {
                invalid()
            }
        }
```

本来以为63是什么Magic value，问了下GPT知道，原来这是EIP150,也就是63/64法则。  
假设当前有一条调用链EOA => 合约A => 合约B,开始时EOA为这笔支付给了1000Gas  
那么根据EIP150，每次调用时转发给后面合约的Gas不会是当前剩下的所有Gas，而是floor(leftGas \* 63 / 64), 也就是有1/64是会被EVM拿走，拿走之后也并不会分配，而是直接销毁掉。这样的效果就是，函数不能过于大量递归来侵占资源，在一些调用后很快就会被抽光Gas导致OOG。  

而为什么类似于forwarder之类的合约会使用这样的判断呢，目的就是看看此时剩余的Gas是否充足，有没有被target用掉太多Gas导致forwarder自己后续的逻辑无法执行，如果剩余的Gas已经非常少了, 那么就用assembly和invalid()来提前终止掉，并把交易回滚。选择用这俩的原因也是因为gas消耗低，防止连终止都发不出来

# 2026-01-20
<!-- DAILY_CHECKIN_2026-01-20_START -->















今天看Certik给Venus的审计报告里学到一些之前在可升级合约中没有注意过的东西。  
首先我们知道最常见的namespace写法是在ERC1967中给的实现合约SLOT,也就是这样

```
bytes32(uint256(keccak256("eip1967.proxy.implementation")) - 1)
```

与此同时oz方案有时候会这样写:

```
keccak256(abi.encode(uint256(keccak256("openzeppelin.storage.ReentrancyGuard")) - 1)) 
```

相当于多做了一次keccak256来把hash值变换得更自然hash的样子  
而ERC7201，需要写成这样子

```
keccak256(abi.encode(uint256(keccak256("openzeppelin.storage.ReentrancyGuard")) - 1)) & ~bytes32(uint256(0xff))
```

去做& ~bytes32(uint256(0xff))的结果是将hash的最低位的8个bits置0，核心目的是为了扩展性，在实用中假设起始slot经过上述变换后成为了0x123...ab, 接下来如果写新的slot的话，将会使用到0x123...ab+1。而ERC7201要求将所有namespace的最低8位都置为0，也就是至少需要从0x123.....00写到0x123......ff才能跳到"下一页"，来避免跳到别的namespace的slot去。这个可扩展的slot长度显然为0xff, 99%合约不会用超过20个slot，因此显然是够用的。而前248位由于是来自于多重keccak256，也就是这种情况下前面的hash完全相同的概率近似于1/2^248, 因此可以忽略不计。实际上在生产场景下，这个防碰撞的效果是微乎其微的，但是我们无法从数学角度形式化证明hash结果绝对不会碰撞，因此ERC7201的Slot扩展方法就是为了进一步防止这种超低概率事件的发生。  
  
TStore/Tload, 在看Venus审计报告的过程中，看到他们的ReentrancyGuardTrensient合约，这是一个Gas成本更低的ReentrancyGuard，核心是引入了EIP1153中提出的TStore和Tload。mstore和mload的数据只在当前call frame中可见，每次call和delegatecall都会有新的call frame，但是等回调的时候已经是新call frame了，所以mstore和mload做不了reentrancyGuard，因此传统方法都是使用sstore和sload，但问题是这两个opcode的成本很高。而tstore和tload在于它们是同交易的读写指令，生命周期为一个tx，并且opcode的gas花费显著低于sstore和sload，但是又能做到防reentrancy的所有需求，因为ReentrancyGuard的业务范围也是单tx的。本质上ReentrancyGuardTrensient就是用ERC1802这种namespace模式给定这个写标记的slot，然后用tstore和tload来在这个slot中进行读写来做重入锁，然后tx结束后自动回收slot中的数据。但是当前solidity并没有给出高级调用，因此还需要使用assembly inline或者自己把YUL代码包装成一个函数，solidity 0.9.0开始也许就支持了吧。

今天开始开始接触了形式化验证，希望接下来的bootcamp时间里可以学会基本的形式化验证吧。  
周末学得不算多，主要以了解基础为主。  
首先是区别于常规的单元测试和fuzzing测试，形式化验证是采用数学验证的方式保证所有路径在数学性质上必然不会失效。用在一些容易量化的场景下非常好用，例如验证复杂Staking系统中用户可领永远不超过设定的奖励阈值，或者Lending协议中永远不会出现费率倒挂(例如借款利率必然高于提供LP的利率，否则用户直接借出钱来存钱套利)。  
形式化验证主要分为建模，写spec语言定义规则，求解。个人感觉最重要的就是建模了，因为在复杂Defi协议中，如何正确建模数学模型其实是非常困难的。  
目前求解器选择的是certora prover，接下来会继续分享certora的spec语法学习。  
小tips：建模形式化验证时，可以把需要验证的合约拆成harness，即包含需要测试的性质所需的最小合约，这样可以大幅减少复杂度，代码量，并加快prover收敛速度。

# 2026-01-16
<!-- DAILY_CHECKIN_2026-01-16_START -->



















今天发现相同的行为由不同端承担风险就会从协议的正常行为变成攻击行为。  
例如说交易聚合器多跳，在uniswap之类的协议的swapRouter类的合约中，实际上是没有必要对每一跳进行校验的，因为协议默认这是用户的正常行为，假设说用户拿自己的钱去烂池子里换token，或者说故意拉歪流动性池价格(用户将要自行承担存入另外一个资产来拉歪价格或自己走闪电贷拉歪价格，此时风险在用户端)，然后再拿离谱的价格去剩余跳中换其他的价值币，这样的行为是router所允许的，因为router只在乎执行输入的path和最后检测一下amountMinOut。流动性池和AMM池之类的价格拉歪不是Router的责任，因此在审计中通常也没必要把这样的问题标Risk  
但如果说交易聚合的函数并不是一个只负责执行的交易聚合器，而是协议的一部分并且使用了协议自己的资产先去换资产，并且用户还可以自行构造交易路径等参数。那么此时最好加上白名单token，path中只允许白名单token(根据设计取舍)，但sanity check和oracle check是必须要的，通常通过多源TWAP来check。如果没有检查，此时可以考虑给critical或high risk  
实际上这两个函数在实现上几乎是一模一样的，但承担风险的角色不一样的时候，审计的角度和开发应该做的防护是不一样的。这是我觉得今天总结的最核心的原则。  
除去技术相关的问题以外，今天还有感触就是其实需要对大产品去魅，今天看了下pancakeSwap的审计报告，关于syrup token做得确实有够差，高度怀疑是当年抄代码但是没抄明白，抄下来没有理解设计机制后用错了，从而导致syrup失去治理功能了(主要问题出在\_moveDelegateeVotes的参数错误上)。算是印证了DYOR的原则。

# 2026-01-15
<!-- DAILY_CHECKIN_2026-01-15_START -->




















今天有点发烧，没怎么做很多事情，只有一些比较简单的东西来记录一下。  
今天审了份ERC20相关的合约。发觉到其实许多的ERC20代币都有高中心化风险，因为ERC20在没有丢弃权限时，很多时Mint权限是在某个地址上的。结合昨天Web3安全分享会中老师分享的Safe被劫持的事件，以下是一些小的见解。  
在许多项目中，项目方不丢弃权限但是会采用多签钱包去控制权限。在昨天的分享会之前，实际上我也认为多签+时间锁已经足够安全了，但是昨天的会议中得知，多签也会有问题，这就意味着这个路径有一定风险，应该归为Low-Risk(如果单钱包权限是High-RIsk的话)。  
那么在目前最安全的做法应该要是DAO+时间锁+挑战期(如果不考虑操作时效的话), 因为即使是多签，仍然有多签的所有人员都被定向劫持了钱包。但攻击者无法劫持这么多DAO成员的钱包去做投票，最终的执行者钱包需要先校验DAO提案是否通过，如果DAO提案通过的话，再由多签钱包负责执行。那么在这样的流程中，相对DAO而言比较中心化的多签钱包只能做执行，而不能随心所欲的操作，这个时候就能有效减少作恶风险了。  
目前来说是这么思考的，等不发烧了再来仔细思考一下会发生的其他side-effect和应该如何防范。

# 2026-01-14
<!-- DAILY_CHECKIN_2026-01-14_START -->





















今天在做一些自己的事情，由于我的工作是智能合约审计，因此记录一下今天审计带来的一些开发时的思考。  
  
审计目标是一份借贷协议的controller, 也是这个协议的entry point.其中的分桶抵押机制，也就是稳定抵押品只能借出高波动难清算的抵押品，反之亦然。项目方的目的是为了防止高波动资产能作为抵押高波动抵押品的情况。  
  
现假设稳定抵押品为A，高波动抵押品为B，A的有效担保抵押价值为cA，稳定抵押品和高波动抵押品的风险因子分别为rA，rB。  
此协议的问题在于，正确做法下取出A时，要么减少cA，要么提高rB，但是开发者提高了rA。  
攻击者可以存入大量A来提高rB，从而借出大量的B，然后抽走抵押的A，此时的rB不变，再重复存入A，进一步推高rB，等到rB允许借出池中所有B时，此时攻击者存入池中的A的抵押价值远小于此时攻击者借走的B，这个时候直接不还借走的B，赔偿抵押的A，攻击者就偷走了资产把坏账留给了B池。由于操作都在同块进行，而抵押率不足的清算需要等价格在下一块更新后才能清算，因此攻击者用少量A借出大量B的行为也不会被清算，等清算的时候攻击已经完成了。  
  
总结的开发者应该注意的点有几个：  
1.注意拼写，尤其是命名近似且相同数据类型相同场景下使用的数据容易写错导致严重漏洞，但是编译器并不会报错，在不涉及当前路径的操作中，也难以发现漏洞。  
2.用户可组合操作资金的功能可以考虑跨块执行，避免同块执行，避免预言机离散更新的间隔导致整个协议的攻击面扩大。可以考虑加入cooldownBlock或cooldownTimeStamp(抵押借贷等场景推荐cooldownBlock)来禁止同块执行或大于预言机时间更新窗口(但加入这一防护后无法使用闪电贷)。这一举措可以减少整个协议的闪电贷攻击风险与清算不及时的风险。

# 2026-01-13
<!-- DAILY_CHECKIN_2026-01-13_START -->






















今天的co-learning有在听到讨论DAO治理怎么样公平。其实很难去有一个完全公平的体制。  
但是之前有想过一个DAO架构，1token1票，但是权重根据token越多增长得越少，相当于给巨鲸加入了一个边际递减。  
与此同时，给每个地址去量化当前地址的声誉与贡献，也加入投票的权重中，避免巨鲸可以把大量token分散到多个地址来绕过token数量带来权重影响的边际递减。  
再在这个时候在有一定质押量的地址中随机抽取12个（也可以更多），作为公民裁决团。  
大致的架构就是DAO成员根据上述的权重计算规则先投一次票，再看公民裁决团投票之前的DAO成员投票是否合理。  
但这里又引入了新的问题，如何保证公民裁决团不会投票冷漠？如何保证公民裁决团不会串通好然后在本次投票形成新的寡头层？如果巨鲸通过钱让很多人创建很多钱包，然后被选上公民裁决团的几率比普通公民大怎么办？  
所以其实仍然是有很多的问题，但对于一个更好的体制，目前确实是没有一个准确的答案。  
但是XiaoHai老师讲到的一个例子让我觉得非常有道理，那就是ETH的硬分叉。  
仔细思考过后我认为，这一点确实是民主的保障。民主很多时候都是由大多数人的共识确立的，让多数人满意了。  
但是问题是，那其他人的想法该怎么办？遵从了多数人的想法后，是不是一种对意见不同的人的少数人的剥削？  
所以此时一个退出机制就很重要，这个退出机制是让不同意当前主流共识的人可以尽量低成本无惩罚的去离开当前的体制，建立自己的体制。也就是我们需要先承认有一些分歧是不可调和的，此时我们需要保障少数人的意见仍然可以生效，那就硬分叉咯。就像民主国家也不能靠投票来保证每个人都满意，但是文明国家都不会限制移民，如果你对体制不满，你可以直接不和这个体制玩了。  
所以我觉得以太坊硬分叉的理念确实是体现了一个非常重要的民主举措。但是到底什么是真正公正的制度，还是需要继续思考。

# 2026-01-12

今天参与了Co- Learning会议，感觉受益匪浅呢。以前没有关注过以太坊的每个层，听完同学们提的问题后研究了一下。  
  
共识层并不知道什么是EVM，什么是智能合约，它只保证区块的有效性合法性。  
  
而执行层应该是可以概括为负责状态的转移，本质上EVM做的许多工作都是不断的sload与sstore的不断进行状态的转移。  
  
Rollup层是自己执行完交易后生成state root等可验证证明，发送到执行层去做验证，验证通过的话就被认为是一次合法的状态转移，并将修改后的状态写入下一个区块中等待验证者打包后给共识层校验区块有效后写入链上。但是Rollup的方案是不同的，ZkRollup是给zk proof，然后执行层验证。optimism是L1先假设这个证明是对的，在一段时间内如果有人有疑问的话可以来挑战，挑战成功的话就不会被验证通过了。
