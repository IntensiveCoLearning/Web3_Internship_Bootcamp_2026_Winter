# SpoonOS 法律助手 笔记

## 一、核心目标

构建一个 **有法律依据、可验证、可追溯** 的 AI 法律助手：

-   基于真实法律条文回答问题
    
-   避免 AI 幻觉
    
-   支持区块链证据存证
    

* * *

## 二、法律检索原理（RAG）

-   将法律条文离线 **向量化并建立索引**
    
-   用户问题同样转为向量
    
-   通过 **语义相似度搜索** 找到相关法条
    
-   将检索结果交给 Agent 推理回答
    

本质：**向量语义搜索 + LLM 推理**

* * *

## 三、Agent 工作方式（ReAct）

1.  判断是否为法律问题
    
2.  自动调用 `search_laws` 检索法条
    
3.  基于检索结果生成回答
    

AI 不直接编答案，而是 **“先查法，再回答”**

* * *

## 四、证据上链原理

-   不上链原文，只上链 **内容 Hash（指纹）**
    
-   Hash + 时间戳写入区块链
    
-   任何人可通过重新计算 Hash 验证证据真实性
    

实现 **不可篡改 + 可时间证明**

* * *

## 五、项目亮点

-   RAG + Agent 的法律问答架构
    
-   AI 法律结论可区块链确权
    
-   回答具备 **依据性与可验证性**

## Uniswap V4 学习笔记

### 一、Uniswap V4 的定位与核心目标

Uniswap V4 并不是对 V3 的简单升级，而是一次**架构级重构**。核心目标可以概括为三点：

1.  **极致 Gas 优化**  
    通过单一合约（Singleton）架构，显著降低池子创建、Swap、跨池操作的 gas 成本。
    
2.  **高度可定制的 AMM 逻辑**  
    通过 Hooks 机制，将 AMM 的“可变逻辑”外置，允许开发者在不修改核心协议的情况下扩展功能。
    
3.  **更强的协议组合性**  
    支持原子级的跨池操作和复杂交易路径，方便构建高级 DeFi 策略。
    

* * *

### 二、Singleton 架构（最重要的变化）

从 Factory + Pool 到 Singleton

在 Uniswap V2/V3 中：

-   每创建一个池子，就会部署一个独立的 Pool 合约；
    
-   Factory 负责创建和管理池子。
    

在 **Uniswap V4** 中：

-   **所有池子共享一个核心合约（Singleton）**；
    
-   池子的状态（储备、价格、Tick、流动性等）以 **结构化数据** 的形式存储在 Singleton 内。
    

**好处**

-   不再为每个池子部署合约，极大降低部署和调用成本；
    
-   跨池 Swap 不需要多次外部合约调用；
    
-   更适合多跳交易和复杂路由。
    

* * *

### 三、Hooks：V4 的灵魂机制

什么是 Hook？

Hook 是在 Swap / Mint / Burn 等关键生命周期节点上被调用的 **外部合约逻辑**。

每个池子在创建时可以绑定一个 Hook 合约，该 Hook 可以选择性实现以下回调：

-   `beforeSwap` / `afterSwap`
    
-   `beforeInitialize`
    
-   `beforeModifyPosition` / `afterModifyPosition`
    
-   `beforeDonate` / `afterDonate`
    

这些 Hook **可以改变交易行为本身**。

* * *

Hook 能做什么？

Hooks 几乎让 V4 变成了一个 **AMM 操作系统**：

-   动态手续费（根据波动率、交易量调整）
    
-   内置 TWAP / Oracle 逻辑
    
-   MEV 防护（限制区块内多次交易）
    
-   自动再平衡 LP 头寸
    
-   限价单 / 止损单
    
-   稳定币曲线、CFMM、Hybrid AMM
    
-   协议级税收 / 激励
    

**V4 不再是“一个 AMM”，而是“AMM 框架”**

* * *

### 四、Flash Accounting（闪电记账）

Uniswap V4 引入 **Flash Accounting**，允许在一次交易中：

-   多次修改池子状态；
    
-   最后统一结算 Token 的净流入 / 流出。
    

类似“记账在内存中，结算在最后”。

**好处：**

-   支持复杂多跳 Swap；
    
-   原子性强，不中途转账；
    
-   极大减少 ERC20 transfer 次数，降低 gas。
    

* * *

### 五、Native ETH 支持回归

在 V2 有、V3 没有的一个特性，在 V4 中回归：

-   V4 **原生支持 ETH**，不再强制使用 WETH；
    
-   减少 Wrap / Unwrap 操作，降低 gas；
    
-   对用户和前端更友好。
    

* * *

### 六、费用与激励机制

-   手续费模型可由 Hook 控制；
    
-   协议费、LP 费、外部激励可灵活拆分；
    
-   为未来的 MEV Capture、协议激励提供基础。

### Uniswap V3 笔记

Uniswap V3 是一种基于 **集中流动性（Concentrated Liquidity）** 的自动化做市商（AMM），核心改进在于允许流动性提供者（LP）将资金集中在指定的价格区间内，而不是像 V2 那样在 (0,+∞)(0, +\\infty)(0,+∞) 全区间提供流动性，从而显著提升资本效率。

在 V3 中，价格不再直接表示为 `reserveA / reserveB`，而是以 **Tick** 为离散单位进行刻度化。每个 Tick 对应一个固定的价格区间，价格以 `sqrtPriceX96`（Q64.96 定点数）形式存储，使得价格计算和区间移动更加高效、精确。流动性只在当前价格所在的 Tick 区间内生效，当价格跨越 Tick 边界时，会触发流动性增减（liquidity net change）。

与 V2 的 LP Token 不同，Uniswap V3 中每一份流动性头寸都是 **NFT（ERC-721）**，其唯一标识了：

-   token0 / token1
    
-   费率等级（0.05% / 0.3% / 1%）
    
-   价格区间（tickLower, tickUpper）
    
-   流动性数量
    

这使 LP 能精细化管理仓位，但也引入了主动管理成本。

手续费机制上，V3 将手续费 **按头寸独立累计**，只有当价格在 LP 设置的区间内发生交易时，该头寸才能赚取手续费；当价格脱离区间，LP 头寸将“失效”，仅持有单边资产，不再产生手续费。

在交易执行层面，Swap 不再是单一池子的线性过程，而是沿着 Tick 连续“吃”流动性区间，逐段计算价格变化与输入输出数量。这使得 V3 在大额交易时具有更好的价格发现能力，同时也对前端和数据解析提出了更高要求。

总体而言，Uniswap V3 用 **复杂度换取资本效率**：  
它极大提升了 LP 资金利用率和协议手续费收入，但也提高了 LP 的专业门槛，并推动了自动化做市策略、LP 管理工具和数据分析基础设施的发展

### Uniswap V2 学习笔记

Uniswap V2 是以太坊生态中最具代表性的 **AMM（Automated Market Maker）去中心化交易协议**，通过智能合约实现无需订单簿的代币交换。其核心定价模型为恒定乘积公式 **x · y = k**，其中 x、y 分别表示池中两种代币的储备数量，k 在交易前后保持不变（忽略手续费）。

1\. 流动性池与 LP 机制

每一个交易对对应一个独立的流动性池（Pair 合约），池中资产由流动性提供者（LP）按当前价格比例存入。  
LP 会收到 **LP Token（ERC-20）**，代表其在池中的份额，可用于赎回本金和手续费收益。  
当用户移除流动性时，按其 LP Token 占比取回两种资产。

2\. 交易与手续费

Uniswap V2 中每笔交易都会收取 **0.3% 的手续费**，手续费不会单独分离，而是直接计入池子储备中，从而提升 k 值，间接分配给所有 LP。  
由于价格完全由池中资产比例决定，大额交易会显著改变储备比例，产生 **滑点（Slippage）**，这也是 AMM 模型的典型特征。

3\. 路由与 ETH 处理

V2 支持 **ERC-20 ↔ ERC-20 直接交易**，不再强制通过 ETH 作为中介，提高了交易效率。  
同时，引入 **WETH** 作为 ETH 的封装版本，使 ETH 可以像普通 ERC-20 一样参与交易与流动性提供。

4\. 价格预言机（TWAP）

Uniswap V2 内置了基于区块时间累计价格的 **TWAP（Time-Weighted Average Price）机制**，可以在一定程度上抵御短期价格操纵。  
许多 DeFi 协议（如借贷、衍生品）会使用 Uniswap V2 的 TWAP 作为去中心化价格参考。

5\. 风险与局限

Uniswap V2 的主要风险包括：

-   **无常损失（Impermanent Loss）**：当池内价格相对外部市场发生较大偏离时，LP 收益可能低于单纯持币
    
-   **资本效率较低**：流动性在整个价格区间均匀分布，导致大量资金并未被有效利用
    

尽管存在局限，Uniswap V2 仍然奠定了 AMM DEX 的基础设计范式，为 Uniswap V3 的集中流动性模型以及后续大量 AMM 协议提供了重要参考。

**ERC-1155：多代币标准（FT + NFT）总结**

ERC-1155 是一种**多代币合约标准**，允许在**同一个合约**中同时管理同质化代币（FT）和非同质化代币（NFT），每种代币通过 **tokenId** 区分。

**核心特点**

-   **多类型代币**：一个合约支持 FT、NFT、半同质化代币（SFT）。
    
-   **批量操作**：支持批量转账、批量铸造，显著降低 Gas 成本。
    
-   **统一接口**：用 balanceOf(address, id) 查询余额，逻辑更简洁。
    
-   **安全接收**：通过 onERC1155Received 防止误转。
    
-   **高扩展性**：适合复杂资产模型。
    

**典型应用**

-   游戏道具（可堆叠物品 + 唯一道具）
    
-   预测市场头寸（如 YES/NO 代币）
    
-   NFT 碎片化、门票、会员凭证
    

**对比 ERC-20 / ERC-721**

-   比 ERC-20 更灵活（支持多 tokenId）
    
-   比 ERC-721 更高效（批量操作、省 Gas）

## 节点间的连接与通信方式（精简总结）

以太坊节点的通信流程可以概括为三步：  
**找节点 → 建连接 → 传消息（八卦 + 拉取）**

* * *

### 节点发现（UDP + Kademlia）

**目标**：从“谁也不认识”到“有一堆邻居”。

-   新节点启动后，先联系 **引导节点（Boot Nodes）**
    
-   使用 **Node Discovery 协议（discv4 / discv5）**，基于 UDP
    
-   核心交互：
    
    -   `Ping / Pong`：确认节点是否在线
        
    -   `FindNode / Neighbors(Nodes)`：获取更多节点地址
        
-   通过不断向新节点询问邻居，逐步填满本地邻居表
    

**Kademlia 思想**：

-   每个节点有 256-bit ID
    
-   距离用 **XOR** 衡量
    
-   查找节点时，每一跳都逼近目标 ID，提高发现效率
    

**小结**：

> 发现阶段 = 用 UDP + Kademlia 快速找到一批可靠邻居

* * *

### 建立安全连接（TCP + RLPx / devp2p）

**目标**：从“认识”升级为“稳定、安全通信”。

-   节点之间通过 **TCP** 建立可靠连接
    
-   在 TCP 之上运行 **devp2p 协议栈**
    
-   底层由 **RLPx** 负责：
    
    -   密钥握手，建立加密通道
        
    -   在一条 TCP 连接上复用多个子协议（capabilities）
        

常见子协议：

-   `eth/*`：区块、交易同步（执行层）
    
-   `les`：轻客户端服务
    

**小结**：

> TCP 提供稳定管道，RLPx 提供加密与多路复用

* * *

### 消息传播（Gossip + 请求-响应）

**目标**：让交易和区块尽快传遍全网。

Gossip（广播式）

-   新交易 / 新块随机转发给邻居
    
-   邻居再继续转发
    
-   多轮后覆盖全网
    
-   优点：去中心化、鲁棒、传播快（秒级）
    

> 类比：办公室传八卦

请求-响应（按需拉取）

-   用于补历史数据或状态
    
-   精确请求指定区块、区块体、状态等
    

> 类比：去档案室查旧资料

# Web3 入职法律风险

## 一、Web3 用工模式的特殊性

Web3 项目多采用境外注册结构（新加坡、开曼、BVI 等），常见特征：

-   项目方在中国境内无注册主体
    
-   远程办公为主（Telegram / Zoom 协作）
    
-   难以签订有效《劳动合同》
    
-   无法依法缴纳五险一金
    

由此带来的直接影响：

-   薪资纠纷、工伤事故难以适用《劳动合同法》维权
    
-   社保、公积金缺失将影响落户、购房、贷款、子女教育等现实权益
    
-   即使有书面合同，也可能因主体不合格被认定无效
    

部分项目采用 **EOR（名义雇主）** 模式解决合规问题，但在纠纷中，劳动关系认定仍存在不确定性。

**入职前需自我评估：**

-   是否接受灵活用工关系
    
-   是否能接受无社保、公积金
    
-   重要岗位或长期入职，建议提前咨询专业律师
    

* * *

## 二、薪酬结构及法律风险

Web3 常见薪酬模式：

-   人民币 + Token
    
-   全 USDT
    
-   Token 为主要收入来源
    

主要风险点：

-   法律上，工资应以人民币支付，虚拟币支付工资可能被认定无效
    
-   若 Token / USDT 不计入工资：
    
    -   实际工资基数降低
        
    -   影响社保、经济补偿计算
        
-   项目自发 Token 价格波动大，项目失败时可能直接归零
    

结论：  
**Token 薪酬更接近高风险激励，而非稳定收入。**

* * *

## 三、虚拟货币出金风险

由于薪资含虚拟币，员工通常需通过 C2C / OTC 出金：

-   场内挂单
    
-   场外担保交易
    
-   私下交易群
    

主要法律风险：

-   对手资金涉赌、涉诈 → 银行卡冻结
    
-   可能被要求退赔涉案金额
    
-   高价出 U、协助换汇 → 帮信罪风险
    
-   情节严重 → 洗钱、掩饰隐瞒犯罪所得罪
    

**风险防范建议：**

-   尽量保留部分法币薪资
    
-   出金选择相对合规、可追溯渠道
    
-   避免灰色交易、异常高价交易
    
-   留存交易记录与资金来源证明
    

* * *

## 四、项目合法性审查要点

即便不是核心负责人，参与非法项目仍可能被牵连。

入职前建议重点核查：

-   是否存在 Token 融资或收益承诺
    
-   Token 分发机制与经济模型
    
-   是否面向中国大陆用户
    
-   是否存在返利、多级推广结构
    
-   白皮书内容是否涉及投资回报
    

原则：  
**项目本身不合规，个人风险无法完全切割。**

* * *

## 五、学习小结

-   Web3 入职 ≠ 传统劳动关系
    
-   用工、薪酬、出金均存在法律灰区
    
-   高收益往往伴随高合规风险
    
-   入职前审查项目与用工结构至关重要

# Web3 合规性要求与常见法律风险

## 一、Web3 行业法律环境概览

自 2017 年起，中国监管部门持续加强对虚拟货币相关活动的监管，核心政策要点包括：

-   明确禁止 ICO（首次代币发行）等代币融资行为
    
-   禁止虚拟货币交易所运营及撮合服务
    
-   明确虚拟货币不具有法偿性，不得作为支付工具
    
-   禁止境外交易平台向中国境内居民提供服务
    
-   严厉打击以虚拟货币为载体的非法集资、传销、洗钱、赌博等行为
    

总体监管思路可以概括为：

> 全面封堵虚拟货币的金融属性，对区块链技术本身保持有限容忍。

因此，Web3 作为技术栈并未被整体否定，但一旦涉及代币发行、融资、交易、矿池运营等高风险场景，即可能面临行政或刑事风险。

* * *

## 二、主要法律风险类型

### 1\. 代币发行与交易相关风险

中国法律明确禁止任何单位或个人通过 ICO、IEO、IDO 等方式进行融资活动。

需要注意的是：

-   不论代币名称（治理 Token、积分、凭证等）
    
-   不论发行方式（空投、白名单、内部测试）
    

只要代币具备以下特征之一，均可能被认定为非法金融行为：

-   具备融资功能
    
-   具有公开或变相流通性
    
-   伴随收益预期
    

在实践中，若筹资规模扩大，项目方可能面临非法吸收公众存款罪等刑事风险。

此外，技术人员若参与以下环节：

-   代币经济模型设计
    
-   空投与分发逻辑配置
    
-   智能合约部署与运行
    

通常难以仅以“提供技术服务”为由免责，可能被认定为共同行为人。

* * *

### 2\. 赌博与传销相关刑事风险

Web3 项目的经济模型设计直接影响其合规风险。

常见高风险结构包括：

-   充值 → 随机收益 → 可提现
    
-   抽奖、盲盒、转盘等随机激励机制
    
-   链游中以虚拟币或稳定币参与的博弈结构
    

上述模式若形成“下注—随机回报—兑现”的闭环，可能被认定为开设赌场罪。

在 NFT 项目、DAO 或挖矿平台中，若存在以下机制：

-   邀请返利
    
-   多级分佣
    
-   团队计酬
    

一旦构成层级推广关系，可能触及组织、领导传销活动罪。

* * *

### 3\. 场外交易（OTC）与洗钱风险

虚拟货币在场外交易中，常被用于规避外汇监管。

典型风险路径包括：

-   使用人民币购买 USDT、ETH 等虚拟货币
    
-   通过链上或境外平台兑换外币
    
-   实现跨境资金转移
    

该行为可能构成非法经营外汇业务。

更严重的情形是：

-   交易对手或资金来源涉及电信诈骗、赌博、毒品等犯罪
    
-   参与者即便主观上不知情，也可能被认定为协助洗钱
    

因此，参与虚拟货币兑换需高度谨慎，避免成为非法资金流转链条的一环。

* * *

### 4\. 民商事纠纷风险

在司法实践中，虚拟货币相关交易多被认定为合同无效，风险自担。

主要表现为：

-   虚拟货币买卖合同不受法院支持
    
-   因价格波动、对价不明、交付失败产生的纠纷，维权困难
    

委托他人代投虚拟货币亦存在较高风险：

-   投资亏损或资金去向不明
    
-   可能引发民事赔偿责任
    
-   情节严重时，可能被认定为非法经营或非法集资
    

实践中建议：

-   委托方应明确委托范围、权限和投资限制，并保留证据
    
-   受托方不得擅自扩大投资范围，不宜接受不特定公众资金
    

* * *

## 三、小结

在当前中国监管环境下：

-   Web3 技术本身不被全面禁止
    
-   涉及代币、资金、收益分配的业务风险极高
    
-   技术人员、运营人员、资金参与者均可能承担法律责任
    

理解合规边界，是参与 Web3 项目的前提条件。

## 去中心化众筹（Crowdfunding DApp）挑战

### 核心目标

设计并部署一个 **基于智能合约的去中心化众筹应用**，让互不信任的用户在**无需中介**的情况下协作筹集资金：

-   **成功** → 资金自动转给目标合约
    
-   **失败** → 每位参与者可安全取回自己的钱
    

* * *

### 关键技能点

-   **状态机设计（State Machine）**  
    管理众筹生命周期（筹款中 / 成功 / 失败）
    
-   **ETH 资金处理**
    
    -   `payable` 函数接收 ETH
        
    -   合约向外部合约转账
        
-   **映射（mapping）**
    
    -   追踪每个地址的出资金额
        
-   **事件（events）**
    
    -   链上记录捐款行为
        
    -   前端监听并展示用户行为
        
-   **外部合约交互**
    
    -   成功后向 `FundingRecipient` 合约发送资金
        

* * *

### 🏗️ 合约核心功能（CrowdFund.sol）

1.  **contribute()**
    
    -   `payable` 函数，接收 ETH
        
    -   更新 `balances[address]`
        
    -   触发 `Contribution` 事件
        
2.  **截止时间（deadline） + 阈值（threshold）**
    
    -   判断众筹是否成功
        
3.  **complete()**
    
    -   成功时，一次性将资金发送给目标合约
        
4.  **withdraw()**
    
    -   失败时，允许用户取回各自的 ETH
        

* * *

### 事件设计（前端关键）

```
event Contribution(address contributor, uint256 amount);
```

-   前端通过监听事件展示所有出资记录
    
-   若使用命名参数（如 `indexed contributor`），前端需通过**参数名**读取，而不是索引
    

* * *

### 开发流程

1.  初始化项目（Scaffold-ETH / SpeedRunEthereum）
    
2.  启动本地区块链 (`yarn chain`)
    
3.  部署合约 (`yarn deploy`)
    
4.  启动前端 (`yarn start`)
    
5.  修改合约 → 重新部署 → 前端自动更新
    
6.  部署到 Vercel 并提交到 SpeedRunEthereum
    

* * *

### 最终成果

-   一个可交互的 **Crowdfunding DApp**
    
-   用户可：
    
    -   质押 ETH
        
    -   查看所有出资记录
        
    -   在成功/失败条件下自动执行对应逻辑
        
-   应用已部署到 **公共网络**

# Polymarket 架构与链上数据解码

## 一、学习目标

-   理解 Polymarket 的核心数据模型：**Event、Market、Condition、Collection、Position(TokenId)**，并能清晰说明它们的层级与关系。
    
-   理解链上日志在 **市场创建 → 交易 → 结算** 全生命周期中的作用，以及日志如何串联形成完整证据链。
    
-   掌握链上日志解析方法，能够实现：
    
    -   **交易解码（Trade Decoder）**：给定交易哈希，还原成交的价格、数量、方向等。
        
    -   **市场解码（Market Decoder）**：给定 conditionId 或创建日志，还原市场参数（问题标识、预言机、抵押品、YES/NO TokenId）。
        

* * *

## 二、核心概念与数据模型

### 1\. Event 与 Market

-   **Event（事件）**：一个预测主题，如“2024 年美国大选”。
    
-   **Market（市场）**：事件下的具体预测问题，通常是二元（Yes / No）。
    
    -   一个 Event 可以包含多个 Market。
        
    -   Market 是实际发生交易的最小单位。
        

### 2\. NegativeRisk（负风险机制）

-   适用于 **多结果、互斥市场**（赢家通吃）。
    
-   通过 **NegRiskAdapter 合约**，将同一事件下的多个 Market 关联起来。
    
-   关键思想：
    
    -   某一 Market 的 **NO 头寸 ≈ 其他所有 Market 的 YES 头寸**。
        
    -   提高资金利用率，避免为每个结果单独提供流动性。
        
-   支持 **NO → 多个 YES** 的头寸转换（convert）。
    

* * *

## 三、CTF（Conditional Token Framework）中的关键对象

### 1\. Condition（条件）

-   市场在链上的唯一登记身份。
    
-   创建方式：调用 `prepareCondition`。
    
-   **ConditionId 计算公式**：
    
    ```text
    conditionId = keccak256(oracle, questionId, outcomeSlotCount)
    ```
    
-   含义：
    
    -   绑定问题、预言机和结果数量，是市场结算的依据。
        

### 2\. Collection（集合）

-   表示在某个 Condition 下选中的结果集合。
    
-   **CollectionId 计算公式**：
    
    ```text
    collectionId = keccak256(parentCollectionId, conditionId, indexSet)
    ```
    
-   Polymarket 中：
    
    -   `parentCollectionId = 0`
        
    -   二元市场：
        
        -   YES → indexSet = 1 (01)
            
        -   NO → indexSet = 2 (10)
            

### 3\. Position / TokenId（头寸）

-   用户实际持有、可交易的资产。
    
-   实现为 **ERC-1155 Token**。
    
-   **TokenId 计算公式**：
    
    ```text
    tokenId = keccak256(collateralToken, collectionId)
    ```
    
-   每个 Market 对应 **两个 TokenId**：YES 与 NO。
    

### 4\. Collateral（抵押品）

-   Polymarket 使用 **USDC（Polygon 上为 USDC.e）** 作为唯一抵押品。
    
-   每 1 份 Outcome Token 背后对应 **1 USDC 的潜在兑付**。
    

### 5\. 价格含义

-   YES 价格 = 市场对“事件发生概率”的定价。
    
-   例：价格 0.60 USDC
    
    -   发生 → 兑付 1 USDC（盈利 0.40）
        
    -   不发生 → 价值归零（损失 0.60）
        

* * *

## 四、市场生命周期与链上证据链

### 1\. 市场创建（Creation）

-   调用：`ConditionalTokens.prepareCondition`
    
-   **关键日志**：`ConditionPreparation`
    
-   作用：
    
    -   确认问题、预言机、结果数量
        
    -   标志市场正式存在
        

### 2\. 初始流动性与拆分（Split）

-   调用：`splitPosition`
    
-   **关键日志**：`PositionSplit`
    
-   作用：
    
    -   锁定 USDC
        
    -   铸造等量 YES / NO 头寸
        

### 3\. 交易撮合（Trading）

-   合约：`CTFExchange` 或 `NegRisk_CTFExchange`
    
-   **关键日志**：`OrderFilled`
    
-   包含信息：
    
    -   maker / taker
        
    -   makerAssetId / takerAssetId（0 表示 USDC，其余为 TokenId）
        
    -   成交数量、手续费
        
-   价格计算：
    
    -   由 USDC 与 TokenId 的成交数量比例得出
        

去重注意

-   一次撮合可能产生多条 `OrderFilled`：
    
    -   maker 侧填单
        
    -   taker 汇总（taker = exchange）
        
-   常见处理方式：
    
    -   过滤 `taker == exchange` 的日志
        
    -   或使用 `OrdersMatched` 作为唯一成交记录
        

铸造 / 合并的隐含逻辑

-   YES 买单 + NO 买单 → 锁定 1 USDC → 铸造一对头寸
    
-   YES 卖单 + NO 卖单 → 销毁头寸 → 赎回 USDC
    
-   对应 `PositionSplit` / `PositionsMerge` + `OrderFilled`
    

### 4\. 结算（Resolution）

-   预言机调用：`reportPayouts(conditionId, payouts[])`
    
-   结果：
    
    -   胜出头寸 = 1 USDC
        
    -   失败头寸 = 0
        
-   用户调用：`redeemPositions`
    
-   市场生命周期结束
    

* * *

## 五、总结：链上可验证的完整证据链

1.  **ConditionPreparation** → 市场参数与预言机绑定
    
2.  **PositionSplit** → 资金注入与头寸生成
    
3.  **OrderFilled / OrdersMatched** → 交易与价格形成
    
4.  **reportPayouts / redeemPositions** → 结果确认与清算
    

> 通过解析这些链上日志，可以在不依赖 Polymarket 前端或数据库的情况下，**完全基于链上数据重建市场的全部历史行为**。

## Layer 2 笔记

## Rollup 技术比较

| 类型 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Optimistic Rollup | 先假设正确，事后欺诈证明 | EVM 兼容性强、成本低 | 提现延迟（约 1–2 周） |
| ZK Rollup | 零知识证明验证状态 | 安全性高、快速提现 | 开发复杂度高、EVM 兼容不完全 |

* * *

-   **Starknet**
    
    -   语言：Cairo（非 Solidity）
        
    -   特点：ZK-STARK，极高扩展性
        
-   **zkSync**
    
    -   工具链：支持 Solidity
        
    -   特点：ZK Rollup，开发体验友好
        
-   **Arbitrum**
    
    -   架构：Optimistic Rollup
        
    -   特点：完全兼容 EVM 工具链（Hardhat / Foundry）
        
-   **Base**
    
    -   背景：Coinbase 推出，基于 OP Stack
        
    -   特点：生态支持强、开发成本低

-   zkRollup 平台 **不保证地址一致性**
    

### 跨链与桥接

-   官方桥：zkSync / Arbitrum Bridge
    
-   第三方协议：LayerZero、Axelar、Wormhole
    
-   需评估 **延迟与费用**
    

### 实践案例

-   Starknet：Cairo NFT 合约 + 前端交互
    
-   Arbitrum：Nitro 模式下的 Gas 竞拍逻辑

# 合约审计笔记

-   **合约不可修改**：一旦部署，漏洞难以修复，审计是关键风险控制手段

-   **法律合规**：部分监管或机构要求提供审计报告

-   **Slither**：静态分析工具，检测常见漏洞与代码规范

-   **MythX**：云端安全分析服务，支持 CLI / API

-   **Foundry**：开发与测试框架，支持模糊测试（Fuzzing）

* * *

1.  **静态分析**：Slither / Mythril 扫描代码缺陷

* * *

## 知名审计机构

## 智能合约安全总结

**一、安全设计基本原则**

-   **最小权限原则**：只授予必要权限，降低被滥用风险
    
-   **模块化设计**：结构清晰，便于审计与维护
    
-   **显式错误处理与事件记录**：提升可追溯性与应急能力
    

**二、常见漏洞类型与防护思路**

-   **重入攻击（Reentrancy）**
    
    -   本质：外部合约在回调中重复调用函数
        
    -   防护：先更新状态，再进行转账（Checks-Effects-Interactions）
        
-   **预言机操纵（Oracle Manipulation）**
    
    -   风险：依赖单一、不可信价格源
        
    -   防护：使用 Chainlink、多源验证、TWAP 等机制
        
-   **整数溢出/下溢**
    
    -   风险：unchecked 使用不当
        
    -   防护：Solidity 0.8+ 内建检查或 SafeMath
        
-   **权限控制缺失**
    
    -   风险：管理函数可被任意调用
        
    -   防护：使用 onlyOwner / AccessControl
        
-   **未初始化代理合约**
    
    -   风险：被他人初始化并接管合约

**Gas 优化总结**

Gas 是 EVM 执行指令的计量单位，每一步操作都会消耗固定 gas。Gas 优化的核心目标是**减少不必要的高成本指令（尤其是 storage 读写）**，从而降低交易费用、提升用户体验。

**常见优化要点：**

1.  **减少存储操作（Storage Write / Read）**
    
    -   第一次 `SLOAD` 约 2100 gas，后续约 100 gas；而内存读取仅约 3 gas
        
    -   `SSTORE` 写入成本高达 20,000 gas
        
    -   多次使用同一 storage 变量时，应先缓存到 memory，集中一次写回
        
    
    ```
    // ❌ 非优化
    balances[msg.sender] += msg.value;
    
    // ✅ 优化（一次读，一次写）
    uint256 current = balances[msg.sender];
    balances[msg.sender] = current + msg.value;
    ```
    
2.  **位压缩（Bit Packing）**
    
    -   将多个小类型变量组合进同一个 `uint256` 存储槽，减少 storage 占用
        
    
    ```
    struct Packed {
        uint128 a;
        uint128 b;
    }
    ```
    
3.  **循环优化**
    
    -   避免在循环中重复读取 `arr.length` 等 storage 值，提前缓存
        
    
    ```
    uint256 len = arr.length;
    for (uint256 i = 0; i < len; ++i) {
        ...
    }
    ```
    
4.  **函数可见性选择**
    
    -   仅供外部调用的函数使用 `external`，比 `public` 更省 gas
        

**一句话总结：**  
Gas 优化的本质是**减少 storage 访问、合并计算、避免重复操作**，把昂贵的链上执行尽量压缩到最少次数。

## 区块链前端整合

区块链前端整合的核心目标，是**让普通用户通过网页与链上智能合约完成交互**，形成完整的“部署 → 使用 → 反馈”闭环。

其中，钱包负责身份与签名，前端负责交互与状态展示，区块链负责最终执行和确认。

技术栈方面，**Solidity 合约 + 前端区块链交互库**是基础能力。Web3.js / Ethers.js 有助于理解流程，但在新项目中更推荐使用 Viem、Wagmi 等现代方案；钱包连接、RPC 节点和部分状态管理通常由第三方组件提供。

通过本章的实例，将已部署在测试网的合约接入 Web 前端，实现留言等功能，完成了从**合约开发到用户可用产品**的关键一步，也真正体现了 Web3 应用“链上逻辑 + 链下界面”的协作模式。

![屏幕截图 2026-01-17 195825.png](https://raw.githubusercontent.com/IntensiveCoLearning/Web3_Internship_Bootcamp_2026_Winter/main/assets/mizuki258/images/2026-01-17-1768651215270-_____2026-01-17_195825.png)

## 《021学习以太坊》第二章总结

在了解以太坊节点和客户端软件之后，逐渐意识到“以太坊不是一条链，而是一套协同运行的软件系统”。所谓节点，本质上就是运行以太坊客户端的服务器；而真正维持网络运行的，是**多种客户端软件之间的协作**。

### Web3运行原理

**交易**本质就是：做什么 + 给多少 Gas + 防重放的 nonce。  
钱包（如 MetaMask）负责把交易组装好、用私钥签名，再广播到链上，签完就能在浏览器里查到。

**数字签名**保证两件事：  
别人能验证“是你发的”，但没人能伪造。私钥一旦泄露，等于账户完全失控。

**Gas 机制**就是手续费系统：  
操作越复杂越费 Gas，网络越堵 Gas 越贵，用来防垃圾交易、激励节点干活。

**交易流程**很简单：  
签名 → 发到网络 → 排队 → 被打包进区块 → 共识确认。  
新区块先是未最终确认，约十几分钟后 Finalized，才算真正不可逆。

**共识机制**：

-   比特币用 POW（拼算力，耗能）
    
-   以太坊用 POS（质押 ETH，当验证者，作恶会被罚）
    

**RPC**是钱包和区块链之间的“入口”，有中心化风险，但多 RPC 并存能降低单点问题。

**智能合约**就是写在链上的程序：  
规则公开、不可随意改，调用时在虚拟机里执行，结果写入区块链。  
本质是把“信任人和机构”变成“信任代码和共识”。

**NFT Mint**本质也是一次合约调用，只是比转账复杂，成功后仍需等待最终确认。

**以太坊升级**靠 EIP 提案推进，社区讨论决定，通常一年 1–2 次硬分叉。

**节点与验证者**遍布全球，多客户端并存，保证网络不因单点故障而失效

# 区块链

定义：区块链是一种去中心化的分布式账本技术，用于在网络节点之间安全、透明且不可篡改地记录事务数据。每条链由一系列按照时间顺序相连的“区块”组成，每个区块内部包含了多笔交易数据及元数据，确保了数据记录的完整性与可追溯性。

特性：**不可篡改 ：**你无法改变历史信息，因为每个区块包含了上一个区块的摘要并串联起来，如果你修改了历史的区块，你将必须修改后面的全部区块

**公开透明、匿名 ：**在区块链上的信息全部公开透明。每个人都可以顺着区块和链找到历史上所有的记录来查看你的钱包余额。但是没人知道这是你的钱包

**快速交易 ：**无论金额多少以及你在什么地方，只要你的交易记录被打包在区块链中，交易就自动完成。相比传统的跨国汇款非常快速便捷。

区块链运行的步骤：

1.  **用户发起交易**：用户通过钱包应用发起转账、智能合约调用等操作
    
2.  **交易广播**：交易信息被广播到整个网络中的各个节点
    
3.  **节点验证**：网络中的矿工节点验证交易的合法性（余额是否足够、签名是否正确等）
    
4.  **打包成块**：通过共识机制（如工作量证明），矿工将验证过的交易打包成新的区块
    
5.  **链接上链**：新区块被添加到区块链上，更新全网的账本状态
