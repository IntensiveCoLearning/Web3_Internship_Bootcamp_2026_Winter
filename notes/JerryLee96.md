：Web3 开发者关系 (DevRel) 指南

​1. DevRel 的十大角色与核心职能

​在 Web3 生态中，DevRel 并不是单一的岗位，通常由多个角色重叠而成。

​核心角色： 技术布道师（内容输出）、社区经理（Discord 互动）、项目经理（任务调配）、开发者市场（SEO/投放）、生态负责人（黑客松规划）等。

​四大价值维度：

​反馈： 收集开发者意见，反馈产品 Bug 或文档痛点。

​赋能： 通过教育、文档、Workshop 降低开发门槛。

​生态： 构建连接，孵化有潜力的项目（如 Monad 的开发者网络）。

​增长： 通过大型活动（黑客松）吸引新鲜血液并产生正反馈。

​2. 开发者体验：最小技术栈 (Minimum Tech Stack)

​一个合格的 DevRel 必须为开发者准备好“第一步”的基建：

组成部分 | 核心要求

Quick Start ：极简模板，让开发者能“一键跑通”并看到核心功能。

示例仓库：提供主流框架（React, Hardhat, Foundry）的全适配模板。

FAQ：基于社区真实报错整理的自查文档。

架构与安全：提供最佳实践,如私钥安全管理、高并发参考设计

迁移指南 ：降低从以太坊或其他链迁移至本链的摩擦。

​3. DevRel 的能力模型

​硬技能：

​Debug 能力： 现场演示（Workshop）时能即时解决报错。

​底层理解： 熟悉共识、执行、存储等底层逻辑。

​技术写作： 把复杂的学术论文/白皮书“讲人话”，降低认知负荷。

​软技能：

​同理心： 站在新手视角审视文档，不以“上位者”姿态对话。

​项目管理： 合理排布文档编写、演讲、活动策划的优先级。

​项目实战：Monad 生态动态

​Monad 特性： 独立 Layer 1 协议，完全等效 EVM，支持单 Slot 最终性，高性能且无缝兼容以太坊开发工具。

​近期活动：

​2026 年 2 月 7 日： 深圳 AI 黑客松。

​Multiverse Hackathon： 总奖金 20 万美金，支持 AI + Token 或纯 AI 智能体项目。

​Q&A 职业建议精华

​关于背景： Web3 是草根的舞台，不迷信高学历。重点在于展现能力和产出。

​入行路径： 建议从“广度”入手。不需要每个领域都是顶级专家，但要能分辨什么是好的开发者体验。

​关于黑客松： 不要纠结获奖率（即便只有 2%），先去做。很多想法只有在实施过程中才会完善，不要给人生留下“要是我当初做了就好了”的遗憾。

​客服转岗： 如果有 API 支持经验，应寻找与“开发者支持”或“技术对接”高度匹配的岗位，而非生搬硬套不相关的职位。

一、 降噪版文字稿：核心领域深度拆解

1\. 研究员 (Researcher) 与 媒体 (Media) 的区别

受众不同： 媒体输出的内容是给“大众”看的，追求流量和通俗易懂；而 VC 或项目方的研究报告是给“LP（出资人）”看的，要求逻辑极其严密、数据 Solid（扎实）。

进阶路径： 如果你想通过写文章入行，不要只做简单的信息搬运。要去拆解底层协议，分析技术优劣。哪怕你只是个学生，只要报告质量够高，VC 会主动来挖你。

2\. 社区经理 (Community Manager/CM) 的真相

不只是聊天： CM 的核心是“情绪管理”和“共识维护”。

高压环境： 你要面对的是社区直接的情绪宣泄（尤其是币价波动时）。这需要极高的心理建设，你要把自己当成一个“量子叠加态”的观察者，稳定住社区的氛围。

入行门槛： 相比技术岗位，CM 更看重沟通能力和对行业文化的理解。

3\. 产品经理 (PM) 的逻辑转换

Web3 的痛点： 现在的 Web3 产品大都处于“第一代”，UI 烂、操作复杂、安全性存疑。

机会点： 下一代产品的机会在于降门槛。谁能把 Gas 费、助记词、链上交互做得像 Web2 一样流畅，谁就是赢家。

二、 针对“零经验”新人的保姆级建议

1\. 如何“创造”背景？

不要等机会： 99% 的人说自己没背景，但背景是可以“造”出来的。

实操路径： 参加黑客松（Hackathon）、给开源项目提 PR（拉取请求）、在推特发深度 Thread、在 Discord 活跃并贡献价值。这些记录就是你最硬的简历。

从小团队开始： 不要迷信大公司。加入一个 3-5 人的初创团队，你能参与从写代码、做运营到跑市场的全过程，这种“全栈”经历在 Web3 极具竞争力。

2\. 学习的“降龙十八掌”

AI 辅助阅读： 现在的时代，不要再死啃书本。直接把 GitHub 上的核心代码丢给 AI（如 Claude/Cursor），让它逐行解释。

追踪资金流： 学习如何看 Etherscan，分析大户（Whale）的动向，理解钱是怎么流动的。在这个行业，钱流向哪里，机会就在哪里。

三、 行业哲学：非线性的人生

非线性增长： Web3 行业不是爬楼梯，而是“跳跃”。你可能因为参与了一个成功的项目，或者写对了一篇研报，在半年内完成传统行业十年的财富或认知积累。

接受“脏乱差”： 分享者反复强调，现在的行业非常早期，像“柴火棍”一样脆弱，但也正因为规则未定，普通人才有“掀桌子”重排座位的机会。

运气与实力的辩证： 运气很重要，但运气是给那些“已经在桌子上玩牌”的人准备的。

四、 核心观点总结（后半部分）

1\. 认知差就是竞争力

Web3 是一个极其透明但又极其复杂的信息场。谁能比别人快 10 分钟理解一个新协议，谁就能获得溢价。

2\. 去中心化的求职观

不要等 HR 打电话。去 Twitter (X) 上直接私信创始人，去 Telegram 群里展示你的研究成果。在 Web3，主动性（Permissionless） 是最高的美德。

3\. 安全是底线

无论是开发还是运营，对“资产安全”和“链上逻辑”的敬畏是生存前提。

五、 关键术语勘误补充

"LP"：Limited Partner，指风投基金的背后出资人。

"PR"：Pull Request，指在 GitHub 上提交代码修改请求。

"Thread"：指在 Twitter 上发布的一系列关联推文，常用于深度分析。

"WAP3"：应为 Web3 的转录错误。

"RUS"：应为 Rust 编程语言。

一、 团队协作与分工：模块化是核心

为了提高效率并避免AI工具导致的思路雷同，建议：

-   分工模块化： 明确每个人的职责（如：开发、设计、Demo筹备、演讲等），避免多人重复劳动。
    
-   设立专人负责Demo： 鉴于评委只有3-5分钟评审时间，专门有一人组织和打磨演示流程是非常合理的。
    
-   情绪管理： 沟通不畅易导致不快。明确的分工能让成员专注自身领域，减少摩擦；若发生冲突，应回归“按时交付”的目标进行冷静沟通。
    

二、 选题策略：命题作文 vs. 创意驱动

瑞老师和科德老师提出了两个互补的选题视角：

“命题作文”逻辑：

研究赞助方和项目方的真实需求（如特定公链需要预测市场来带流量）。

针对大赛提供的技术框架（如AI Agent开发框架）去解决其实际应用场景。

“趣味与痛点”驱动：

关注生活中的小痛点（如：曼谷堵车、扫描二维码抽奖的概率问题）。

不必强行对齐宏大叙事，一个有意思的创新点（Spark）往往更能打动评委。

三、 演示（Demo）环节：5分钟抓住注意力

演示是决定胜负的关键，两位老师分享了“防翻车”经验：

录制视频： 强烈建议**提前录制Demo视频**并进行剪辑/加速，配合现场解说，避免实时操作出现Bug或网络卡顿。

逻辑结构： 采用“**问题-方案-实现**”的逻辑，重点突出项目的核心亮点和创新点，不要沉溺于技术细节。

故事化引入： 用生动的小故事（如现场的水瓶二维码）作为开头，迅速吸引评委兴趣。

四、 48小时冲刺指南

面对最后48小时的压力，科德老师给出了“心理按摩”与实操建议：

时间很充裕： 借助AI编程工具，现在的开发效率远超以往。

优先跑通MVP（最小可行性产品）： 不要追求完美功能，先实现一个能证明核心创意的原型。

非技术背景切入： 鼓励设计师或非开发同学利用AI工具（半小时内上手）进行协作，或从流程自动化的角度寻找AI Agent的应用点。

一、什么是 Vibe Coding？

Vibe Coding ≠ 不写代码

而是：

“感觉驱动 + AI 执行”的开发方式

核心特征：

人负责方向、判断、决策

AI 负责拆解、实现、补全细节

快速试错、快速收敛

开发从精细控制变成过程引导

二、Vibe Coding 时代的角色变化

AI 写大部分代码

人负责目标与边界

表达清晰度决定效率

Debug 靠结构

开发者正在转型为：

AI 驱动的技术负责人 / 产品型工程师

三、“快速落地”的真正含义

会议中反复强调的一点是：

快，不是“写得快”，而是“决策快、验证快、回滚快”。

真正的快速落地包含 3 层：

快速明确要做什么

快速让 AI 产出一个可验证的形态

快速判断继续 / 放弃 / 重构

四、优雅落地的核心方法论

-   把 AI 当成“团队”，而不是工具
    

不同模型 = 不同角色

Prompt = 岗位说明书

多轮对话 = 评审会议

你不是在“用 AI”，而是在管理 AI。

-   工作流比代码更重要
    

**一个可复用的 Vibe Coding 工作流**：

需求描述（我要解决什么问题）

可行性分析（是否值得做）

架构草图

模块拆分（职责清晰）

实现计划（AI 可执行）

生成代码 / Demo

快速测试与修正

结论：

先有流程，再有代码。

-   模块化
    

模块化不是为了复杂系统，而是为了：

防止 AI 重复造轮子

快速定位问题

支持随时替换实现方案

AI 参与度极高的开发中，结构决定上限。

-   用文档记录
    

在 Vibe Coding 中：

文档 = 对齐人和 AI 的共识

文档 = 最便宜的记忆体

文档 = 后续迭代的锚点

五、为什么“选题”比技术更重要？

共识：技术已不是最大瓶颈，选题才是。

好的选题具备：

能快速 Demo

能讲清楚价值

能被非技术人员理解

在 黑客松/ Web3 项目中：

能被看懂，比写得多更重要。

六、MVP 在 Vibe Coding 时代的定位

MVP 是“**表达核心想法的最小形态**”

不是完整产品

允许 Mock 数据

允许不优雅的实现

目标只有一个：

让别人 5 分钟内明白你在做什么。

七、对 Web3 / 新时代开发者的启示

代码能力在降权，决策能力在升权

不会编程 ≠ 无法参与开发

会拆问题的人，将指挥最强的 AI

AI 放大个人能力，也放大认知差距

八、总结

Vibe Coding 不是偷懒，而是一种更高级的工程协作方式。

真正的“快”，来自结构清晰，而不是手速更快。

Web3 链上数据分析的深度课程

​

​一、 会议核心内容总结

​1. 链上数据三大基础类型

​交易数据 (Transaction Data)： 最底层的数据，记录转账地址、金额、手续费、交易哈希（身份证）。

​区块数据 (Block Data)： 记录谁打包了交易（矿工/验证者）、时间戳、交易顺序。

​合约数据 (Contract Data)： 预先部署的代码，定义了业务逻辑，涉及 ABI (Application Binary Interface) 解析。

​2. 五大核心数据指标

​会议强调，“为什么关注这个指标”比“如何获取数据”更重要：

​TVL (Total Value Locked)： 衡量 DeFi 协议的市场占有率和信用度。

​活跃地址数 (Active Addresses)： 类似于 Web2 的 DAU/MAU，反映用户增长趋势。

​交易数与交易量 (Tx Count/Volume)： 反映网络热度与资产规模。

​交易费用 (Gas Fee)： Gas\\ Fee = Gas\\ Used \\times Gas\\ Price。反映网络拥堵情况。

​协议收入 (Protocol Revenue)： 衡量协议盈利能力，是投资分析的核心指标。

​3. 数据分析工具矩阵

​基础设施层： Etherscan（最原始的链上浏览器，入门必看）。

​开发/查询层： Dune Analytics（使用 SQL 查询已解析数据，自由度最高）。

​应用/看板层：

​RootData： 项目库+投融资信息（Web3 的天眼查）。

​DeFiLlama： 专注于 DeFi 协议的 TVL 和收入统计。

​Token Terminal： 财务报表视角，适合机构用户进行合规分析。

​二、 对数据方向新人的适用建议

-   ​业务理解 > 编程技能： 不要死磕 SQL 或 Python。AI（如 Cursor、Dune AI）已经能解决大部分代码问题。
    
-   ​核心竞争力在于： **识别哪些指标对当前项目是关键的**。例如：分析 RWA 项目和分析 Meme 币项目的逻辑完全不同。
    
-   ​通过“拆解”学习： \* 去 Dune 搜索热门项目的看板（如 Polymarket），直接看别人的 SQL 逻辑是怎么写的。
    
-   ​通过阅读 VC 的研报（如 Binance Labs, Paradigm），学习专业人士如何构建估值模型和评估指标。
    
-   ​寻找正向反馈： \* 参加社区治理或赏金任务（Bounty）。例如 Optimism 或 Superteam 的数据分析任务，不仅能练手，还能获得代币奖励。
    
-   ​关注英文资源： \* 数据领域的一线动态、新的解析标准通常最早出现在英文 Twitter 和社区中。
    

​三、 知识点扩展与进阶方向

​1. 链上“反洗钱”与“防女巫” (Anti-Sybil)

​会议中提到了一个进阶技巧：如何识别刷量（Wash Trading）或女巫攻击？

​资金源追踪： 检查大量地址的“第一笔 Gas 费”来源。如果 1000 个地址的 Gas 都是由同一个主地址分发的（如每次 0.2 ETH），那么这些地址极大概率属于同一个实体。

​行为模式识别： 检查地址是否在同一时间段进行方向完全相反的交易（左手倒右手）。

​2. AI + On-chain Data 的未来：AI Agent

​自动化解析： 目前最大的痛点是新合约上线没有 ABI 无法解析。未来的方向是利用 LLM (大语言模型) 直接通过字节码（Bytecode）或代币流（Token Flow）识别交易意图（如：这是一笔闪电贷还是套利交易？），无需手动匹配函数。

​3. 估值模型的现实与偏见

​现金流折现 (DCF) vs 相对估值： 虽然传统金融喜欢用 DCF，但在 Web3 中，\*\*相对估值法（P/S Ratio）和注意力经济（Social Signals）\*\*往往更有效。

​提示： 估值不是为了得到一个精确的数字，而是为了确立一个安全边际。

​4. 潜力赛道数据关注点

​RWA (真实世界资产)： 关注链上美债的收益率与底层资产的透明度。

​稳定币： 关注发行量（Circulating Supply）与应用场景的渗透率。

​衍生品 DEX： 关注持仓量 (Open Interest) 与交易者的盈亏分布。

一、会议核心概要（高度浓缩版）

这场讨论围绕 黑客松的完整流程 展开，重点包括：

1️⃣ 选题阶段：为什么很多项目一开始就“输在起跑线”

最大问题：

项目看起来很大、很高级，但

👉 商业逻辑不闭环 / 使用场景说不清

典型反面例子：

做“应用级大而全产品”

没想清楚：

谁用？

为什么非你不可？

你解决的“具体痛点”是什么？

评委第一反应往往是：

「这东西很复杂，但你自己都没想清楚」

✅ 正确思路：

聚焦 一个明确、单点、可演示的需求

宁愿小、窄、简单，也不要“大而空”

2️⃣ MVP & 执行：黑客松不是拼“谁做得全”

黑客松时间极短（8–48小时）

核心目标只有一个：

👉 交付一个“能演示的闭环”

常见共识：

✔ 可以用 mock 数据

✔ 可以砍掉用户系统 / 后台 / 权限

✔ 可以前端只有 1 页

✔ 合约只实现最核心功能

❌ 不允许：没有 Demo、无法展示

一句话总结：

黑客松允许逻辑有瑕疵，但不允许“没有产品”。

3️⃣ 团队结构：不同配置，打法完全不同

A. 技术型团队（技术 > 产品）

可以选：

偏技术创新

用到赞助商 SDK / 链 / 协议

重点讲：

技术突破点

性能 / 成本 / 安全性改进

评委可能真的会看代码（尤其线下）

B. 非技术 / 运营 / 产品型团队

80% 时间想清楚逻辑

20% 时间：

、 核心概念：什么是集中流动性？

V2 的问题： 流动性分布在 0 到 \\infty 的所有价格点上。但对于以太坊（ETH）来说，价格几乎不可能掉到 1 美元或涨到 100 万美元，这导致大部分资金都在“睡觉”，没被用到。

V3 的创新： 允许流动性提供者（LP）自定义价格区间（例如只在 2500 到 3500 之间提供资金）。

视觉化理解： 如果把流动性比作“水”，V2 是把水平均撒在无限长的地面上（水层极薄）；V3 是把同样的水倒进一个窄槽里（水深极高）。

通俗例子： 开了一家换汇所，以前必须准备各种偏门货币，防备有人拿“清朝银票”来换钱。现在你只准备“美元换人民币”，因为这才是大家真正交易的区间。因为你把钱都集中在热门交易区，同样的 1 万元，你在热门区能支撑的交易量远超以往。

二、 为什么要引入 L 和 \\sqrt{P}？（数学简化）

在 V2 中，公式是 x \\cdot y = k。但在 V3 中，因为价格会跨越不同的区间（Tick），k 值会随之变化。

为了合约计算精准且节省 Gas（手续费），天才地引入了：

L (Liquidity)： \\sqrt{k}

\\sqrt{P} (Price)： \\sqrt{y/x}

结论： 这样在计算“价格变动时需要多少币”时，公式变成了简单的线性运算，不再需要复杂的开根号运算。

为什么要这么麻烦？ 因为在区块链上计算“乘除法”很贵，计算“开根号”更贵。把公式预先处理成 \\sqrt{P}，就像是把复杂的菜谱简化成“加一勺盐”，让区块链机器人跑起来更快、更省钱。

三、 Tick（刻度）与手续费分配

Tick 机制： V3 不允许在“任何”价格点随意设置，而是像尺子上的刻度（Tick）一样，每隔一段距离才有固定点位。

手续费分配： 系统会记录每个 Tick 之外的累计手续费。当价格穿过某个区间时，系统就能精算出在这个区间内的 LP 应该分到多少钱。

策略： 区间设得越窄，资金效率越高，分到的手续费越多；但如果价格跑出区间，你就分不到钱了（这就是所谓的无常损失风险）。

四、 生态资源与机会

Unichain 孵化器： 免费线上课程（6周课 + 2周黑客松）。

审计补贴： 如果你开发项目，基金会最高可提供全额的代码审计资助。

黑客松与奖励： 像 Hook Money 这种专注于 DeFi 的黑客松，有数万美元的奖金。

V4 的展望： 提到 V4 引入了 Hooks（钩子），允许开发者在交易的各个环节加入自定义逻辑（如自动限价单、动态手续费等）。

会议强调：

先定目标，再定形式

常见目标分类：

目标

活动示例

拉新

公开分享会、联名活动

激活

内部讨论、共创工作坊

筛选

任务制、报名制活动

教育

系列分享、训练营

如果目标不清晰，活动一定会失败。

第二步：设计活动形式（匹配目标）

会议中隐含的活动形式包括：

分享型（讲 + Q&A）

讨论型（圆桌 / 主题讨论）

共创型（任务、协作）

社交型（破冰、自由交流）

运营原则：

新社区 → 轻、低门槛

成熟社区 → 深、参与感强

第三步：活动前准备（决定成败的 70%）

会议中提到的准备重点：

时间明确

主题足够具体

参与门槛清晰

提前预热

一个好活动标题通常是：

明确对象 + 明确收益 + 明确形式

第四步：活动执行（运营要“在场”）

执行阶段，运营者要做的不是“听”，而是：

控节奏

抛问题

引导发言

照顾新成员

重要能力：

运营不是主持人，而是“气氛调度员”

第五步：活动后复盘

活动真正的价值在活动后

复盘至少回答 4 个问题：

来了多少人？

哪个环节最活跃？

谁是潜在核心用户？

下次怎么改？

并且要做两件事：

内容沉淀（笔记 / 回放 / 总结）

私下连接活跃成员

# 2026-01-18
<!-- DAILY_CHECKIN_2026-01-18_START -->














1.18分享ERC-7962:通过KeyHash +零知识/签名思想,在不暴露用户地址的情况下,证明资产归属,从而解决web3的隐私问题和用户体验问题.

## 问题从哪里来?

NFT本质是ERC-721,在现实中常被用来表示:数字藏品,会员/社区身份

现在的做法:地址=身份 项目方给某个ETH地址mint NFT, 代表你是会员

问题:会员身份是隐私数据,但是在web3中,地址是公开的,一旦用这个地址参与活动,all资产,行为,身份都被关联

**根本矛盾:web3想做去中心化,但实现方式是地址即一切**

现实举例:可以证明是麦当劳会员,但是不要暴露:银行流水,住址,交易记录,

## 为什么是零知识?

核心思想:在不暴露原始数据的情况下,证明某个事实成立.

eg:可以证明X+Y=Z, 他人不清楚X和Y 具体值.

(产品视角):我能向你证明我有资格,但你不需要知道我的身份

ERC-7962 Design将这种思想用在Token/NTF上面

## ERC-7962的核心创新点:

1.  不用ETH地址表示所有权:用KeyHash作为资产所有权标识
    

在链上只知道某个公钥的哈希拥有资产,不知道这个公钥对应的是谁,哪个地址

所有权存在,不暴露身份

2.所有权≠交易发起地址

交易可以由任何地址提交，真正的控制权：来自签名

意味着：用户不需要有ETH,不需要懂Gas,不要暴露地址

3.同时支持NFT和FT

-   ERC-key Hash721(NFT)
    
-   ERC-KeyHash20(FT)
    
-   FT采用类似UTXO的拆分模型
    

这意味着：不只是隐私NFT,而是一个通用的隐私资产模型

设计层面已经考虑：批量转账，Key轮帐，防关联性

## Gas UX 与安全设计

支持

-   Gas sponsorship
    
-   Relayer
    
-   Paymaster
    

安全机制：

-   EIP-712
    
-   nonce
    
-   deadline
    
-   防重放攻击
    

为To C 端的产品，企业级研发，web2用户入门web3做准备

### 优势：

隐私性强

UX极大改善

更加适合Account Abstraction 体系

### 局限性：

Gas 贵

公钥仍然会短暂暴露

不向后兼容

对密钥管理要求更高
