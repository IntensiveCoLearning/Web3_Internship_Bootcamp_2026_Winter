## Web3 开发入门与工程实践

### 一、Web3 开发整体路径的进一步清晰

今天的学习主要围绕 **Web2 → Web3 的实际落地路径** 展开，不再停留在概念层，而是开始真正面对工具链与工程问题。

逐步明确了一个现实结论：  
**Web3 的学习曲线并不是 Solidity 本身，而是整套工程环境。**

包括：

-   本地开发环境（Node / npm / npx）
    
-   智能合约开发框架（Hardhat / Foundry）
    
-   钱包、网络、RPC、Gas 的真实存在
    
-   本地链 vs 测试网（[Localhost](http://Localhost) / Sepolia）
    

这一步标志着从“看教程”进入“真正开发者视角”。

* * *

### 二、Hardhat / Foundry 工具链实践与问题暴露

在实际操作中，今天重点接触并踩坑了以下内容：

-   使用 `npm` / `npx` 初始化 Hardhat 项目
    
-   理解 Hardhat 报错并非“代码错”，而是**项目结构或命令使用方式不对**
    
-   Foundry（forge / cast）在 Windows + Git Bash / PowerShell 下的真实兼容问题
    
-   RPC URL、命令参数、管道符在不同 shell 下的差异
    

一个非常重要的认知是：

> **Web3 开发对“命令行 + 环境理解”的要求，远高于普通前端项目**

这也是很多初学者卡死在第一天的原因。

* * *

### 三、本地链、钱包与“部署”的真实含义

今天对“部署”这件事有了更工程化的理解：

-   本地部署 ≠ 上链
    
-   合约地址 ≠ 永久存在
    
-   钱包 ≠ 一个账号，而是**签名工具 + 私钥管理器**
    

进一步理解了：

-   本地网络（127.0.0.1）只是一个开发用的以太坊模拟器
    
-   临时钱包、测试私钥只是为了让你**敢于失败**
    
-   Sepolia 等测试网才是真正“接近生产环境”的地方
    

这一步完成后，对 Web3 的“去中心化”不再是抽象概念，而是工程事实。

* * *

### 四、Solidity 合约代码的“读代码能力”开始建立

通过阅读合约示例与关卡代码，逐渐开始关注：

-   构造函数是否真的被调用
    
-   函数命名、拼写错误带来的安全问题
    
-   `msg.sender`、`payable`、权限控制的真实含义
    
-   为什么某些合约“看起来没问题，但实际上是漏洞”
    

开始意识到：  
**Web3 安全不是黑魔法，而是对细节的极端敏感。**

* * *

### 五、今天的关键卡点总结

今天遇到的问题并不是“不会写代码”，而是：

-   Windows + Web3 工具链的兼容复杂度
    
-   教程默认你用 macOS / Linux
    
-   错误信息对新手极不友好
    
-   一个参数错误，后面所有步骤都会崩
    

但这恰恰说明：  
**你现在遇到的，是“真实开发者问题”，不是新手幻觉。**

* * *

### 六、阶段性认知升级（非常重要）

今天完成了一个隐性的跃迁：

> 从「我在学 Web3」  
> 到  
> **「我在搭建一个能跑起来的 Web3 开发环境」**

这是绝大多数人中途放弃的分水岭。

## 学习笔记：Foundry & Hardhat 的核心认知整理

### 一、我到底在学什么（从“工具”到“范式”）

Foundry 和 Hardhat 表面上是 **以太坊智能合约开发框架**，但你实际学到的是三件事：

1.  **合约工程化能力**
    
2.  **自动化测试与验证思维**
    
3.  **链上系统的可重复、可验证构建流程**
    

不是“会写 Solidity”，而是：

> 如何像做后端 / 系统工程一样做链上程序。

* * *

### 二、Hardhat：偏工程组织与生态集成

1\. Hardhat 的核心定位

Hardhat 更像一个 **Web3 工程脚手架**：

-   JS / TS 驱动（Node 生态）
    
-   适合：
    
    -   dApp
        
    -   前端 + 合约一体项目
        
    -   多插件协作
        

你通过 Hardhat 实际在学：

-   合约部署流程（compile → deploy → interact）
    
-   本地链 / fork 主网调试
    
-   JS 层如何控制链上行为
    

2\. Hardhat 的“思维模式”

Hardhat 强调的是：

-   **开发体验**
    
-   **工程可读性**
    
-   **生态兼容性**
    

测试本质是：

-   用 JS 写“行为脚本”
    
-   把合约当成黑盒系统去验证
    

👉 更接近 Web2 工程师能快速上手的 Web3 方式。

* * *

### 三、Foundry：偏底层、偏验证、偏系统正确性

1\. Foundry 的核心定位

Foundry 是 **为合约本身而生的工具链**：

-   Rust 编写，极快
    
-   Solidity 原生测试
    
-   几乎不依赖 JS
    

Foundry 让你直面的是：

-   EVM 行为
    
-   Gas、storage、call 细节
    
-   合约的**数学与状态正确性**
    

2\. Foundry 的关键能力

你在 Foundry 里真正学到的是：

-   **测试即规范**
    
-   **状态即真相**
    
-   **失败路径和边界条件**
    

例如：

-   revert 是否符合预期
    
-   fuzz testing 下是否存在隐藏状态
    
-   合约在极端输入下是否仍然安全
    

👉 Foundry 更像是“合约工程师 / 协议工程师”的工具。

* * *

### 四、Foundry vs Hardhat 的本质区别（不是“哪个好”）

| 维度 | Hardhat | Foundry |
| --- | --- | --- |
| 驱动语言 | JavaScript / TypeScript | Solidity |
| 学习曲线 | 平缓 | 陡，但更扎实 |
| 测试关注点 | 行为流程 | 状态与不变量 |
| 工程感 | 强 | 更偏系统验证 |
| 适合场景 | dApp / 产品 | Protocol / DeFi / Infra |

一句话总结：

-   **Hardhat：我在“用合约”**
    
-   **Foundry：我在“证明合约是对的”**

## 一、挑战概览

本挑战通过 **ERC-721（NFT）** 的完整开发流程，帮助理解“代币化”在以太坊中的真实含义，而不仅是停留在图片或炒作层面。

**目标交付**

-   编译并部署一个 NFT 智能合约
    
-   在本地网络完成铸造、转账、所有权验证
    
-   将合约部署到 Sepolia 测试网
    
-   发布一个可交互的 Next.js 前端应用
    
-   理解链上所有权与可组合性
    

**难度与时间**

-   技能水平：初学者
    
-   预估时间：1–4 小时
    

* * *

## 二、核心概念理解

### 1\. 什么是代币化（Tokenization）

代币化可以理解为：  
**为某个物品创建一个可以被钱包持有、被链上识别、可转移的“数字所有权凭证”**。

在以太坊中：

-   所有权由合约代码强制执行
    
-   转移是原子性的、即时的、可追踪的
    
-   不依赖第三方登记系统
    

### 2\. NFT 的本质

NFT（Non-Fungible Token）= 非同质化代币

-   每个 tokenId 唯一
    
-   每个 token 对应一个 owner
    
-   非常适合表示「唯一性资产」
    

NFT 并不等于 JPEG，而是一种 **链上所有权抽象**。

### 3\. 三类被代币化的资产

1.  **现实世界资产（RWA）**
    
    -   股票、房产、黄金
        
    -   需要法律或托管机制把链上转账与链下权利绑定
        
    -   否则只是“收藏品”
        
2.  **链上原生资产**
    
    -   数字艺术、ENS、游戏道具、链上门票
        
    -   代币本身就是资产
        
    -   天然具备全球流通与可组合性
        
3.  **静态 NFT 的再利用**
    
    -   即使 NFT 本身没有功能
        
    -   也可被其他协议读取、组合、金融化
        

* * *

## 三、开发流程总结（按 Checkpoint）

* * *

**工具链**

-   Node.js ≥ 20

* * *

### Step 1：Gas 与钱包机制

**关键认知**

-   Gas 是区块链执行交易的“燃料”
    
-   本地开发阶段使用 **Burner Wallet（临时钱包）**
    
-   临时钱包自动签名，降低学习摩擦
    

**实践要点**

-   使用隐身窗口生成全新地址
    
-   用 Faucet 向该地址转账
    
-   关闭窗口即销毁钱包
    

👉 这是理解“钱包只是私钥管理方式”的关键一步

* * *

### Step 2：NFT 铸造与转账

**完成内容**

-   铸造 ERC-721 NFT
    
-   查看 NFT 列表
    
-   在两个地址间转移 NFT
    
-   理解 ownerOf / balanceOf
    

**核心链上逻辑**

-   `ownerOf(tokenId)`：唯一所有权来源
    
-   `balanceOf(address)`：持仓数量
    
-   `approve` / `setApprovalForAll`：授权模型
    
-   转账触发 `Transfer` 事件
    

**关键理解**

-   NFT 的所有权只存在于链上
    
-   前端只是状态读取器
    
-   钱包只是签名工具
    

* * *

### Step 3：部署到 Sepolia 测试网

**重要变化**

-   从本地 Hardhat → 公共测试网
    
-   需要真实测试网 ETH
    
-   使用独立部署账户（而非个人主钱包）
    

**核心步骤**

-   切换 defaultNetwork 为 sepolia
    
-   `yarn generate` 生成部署账户
    
-   Faucet 充值
    
-   `yarn deploy --network sepolia`
    

👉 这一步标志着：**你的合约真正进入公共区块链**

* * *

### Step 4：发布前端应用

**关键配置**

-   `targetNetwork = chains.sepolia`
    
-   Burner Wallet 默认仅限本地链

**部署**

```

```

前端发布后：

-   任意人可与合约交互
    
-   应用开始具备“Web3 产品”属性
    

* * *

### Step 5：合约验证（Etherscan）

**目的**

-   提升透明度与可信度
    
-   允许他人审计代码
    
-   防止“黑盒合约”
    

**命令**

```

```

验证成功后：

-   合约代码与地址公开可查
    
-   可作为挑战提交 URL

-   NFT ≠ 图片
    
-   NFT = 可被任何合约识别的所有权单位
    

带来的能力包括：

今天的核心学习不在“写简历”，而在如何把一个人的经历，转化成“岗位可识别的价值表达”。

首先意识到一件事：

简历不是经历合集，而是针对目标岗位的一次“证据陈列”。

很多内容不是不重要，而是在当前 JD 语境下不成立，必须被压缩、弱化或暂时删除。

在修改过程中，最大的收获是区分了三种信息层级：

不可动层（事实层）

实习经历、项目是否做过、时间线，这些是事实数据库，不能编，也不该为了好看而改写本质。

可调层（表达层）

同一件事，可以是“我做了什么”，也可以是“我解决了什么问题”“我承担了什么责任”“我如何推进不确定的事情”。

这里的关键不是词藻，而是责任边界是否清晰。

可删层（噪音层）

与目标岗位弱相关、无法在面试中被追问展开、或者只是“显得我很努力”的内容，反而会稀释重点。

第二个重要认知是：

简历不是技术说明书，而是招聘官的“决策辅助工具”。

招聘官关心的顺序是：

你是不是“这个角色要的人”

你是否已经在类似问题上做过决策

你能否在不完整信息下推进事情

所以，好的简历 bullet 必须同时满足：

有动作（你做了什么）

有对象（作用在什么系统/流程/人上）

有判断（你为什么这么做）

有结果（产生了什么影响）

如果只满足前两点，本质是执行者；

加入第三点，才开始像负责人；

第四点决定你是否值得面试。

第三个收获是关于产品/技术边界的理解。

在今天的修改中，一个明显变化是：

不再强调“我会什么工具”，而是强调：

我是否能把模糊需求拆解为可执行模块

我是否能把技术能力转译为业务/产品语言

我是否承担过“对结果负责”的角色，而不只是参与者

这意味着：

“我会 PRD”不是写文档

而是：我能定义问题、约束方案、对齐共识、推进落地

最后一个很重要的反思是：

简历本身就是一次产品迭代。

它同样经历：

需求分析（JD）

信息筛选（经历）

信息架构（版面与顺序）

文案压缩（一页限制）

用户视角验证（招聘官能否 30 秒抓到重点）

今天的改简历，本质是在训练一种能力：

在强约束条件下，做取舍、做聚焦、为结果负责。

产品经理学习笔记

一、今天学习的核心内容

今天主要学习了产品经理的基础认知与核心工作方式，重点放在“产品经理如何思考问题”，而不是具体工具或原型设计。

逐渐理解到，产品经理并不是负责“想功能”，而是负责把模糊的问题拆解清楚，并推动一个可执行的解决方案落地。

二、对产品经理角色的理解

产品经理的核心价值在于定义问题和协调资源，而不是单纯输出想法。

产品经理需要站在用户、业务和技术的交汇点，回答三个关键问题：

用户是谁

问题是否真实存在

这个问题是否值得现在解决

产品做得好不好，往往不取决于功能数量，而取决于是否解决了真实且高频的问题。

三、用户与需求的理解方式

学习中一个很重要的点是区分“用户表达”和“真实需求”。

用户说的话通常是结果或表象，而产品经理需要不断追问背后的原因。例如：

用户为什么会有这个行为

他现在是如何解决问题的

如果没有这个产品，会发生什么

需求分析的关键不在于记录用户说了什么，而在于理解用户为什么这样做。

四、需求优先级与取舍意识

资源有限是产品工作的常态，因此产品经理必须不断做取舍。

并不是所有需求都值得立刻做，也不是用户提到的都要实现。判断一个需求是否优先，通常会综合考虑：

对用户是否有明显价值

是否符合产品当前阶段目标

实现成本和风险是否可控

产品经理的能力，很大一部分体现在“知道什么不做”。

五、从需求到产品方案

从需求到产品并不是一步到位，而是一个逐步清晰的过程。

产品经理需要把模糊的想法拆解成结构化内容，例如功能模块、流程逻辑和使用路径。

产品文档的目的不是写得复杂，而是让所有相关角色对“要做什么、为什么做、怎么做”形成一致理解。

六、产品经理与技术的关系

产品经理不一定写代码，但不能完全不理解技术。

理解技术边界可以避免提出不现实的需求，也有助于在方案阶段做出更合理的取舍。

对有工程背景的人来说，这是一个明显优势，可以更准确地评估实现成本，与开发人员进行更高效的沟通。

七、个人阶段性总结

这次学习让我更加明确：

产品的起点是问题，而不是功能

需求分析的关键在于追问动机

产品工作本质上是持续做决策和取舍

技术背景在产品工作中是加分项，而不是限制

# **用 SpoonOS Graph Agent 构建可解释的对话+占卜应用**

## **1\. 目标与背景**

很多“占卜类”应用会强制抽牌，导致用户无法自然表达情绪。本项目的目标是让用户既能聊天，也能在需要时进入占卜流程，并且每一步都可追踪、可解释。

## **2\. 核心思路：Graph Agent 工作流**

使用 SpoonOS 的 Graph Agent，把流程拆成明确节点：

`parse → route → divination → narration → persist`

-   **parse**：解析用户意图（chat / divination）、领域（love/career/general）、语气等
    
-   **route**：当 intent=divination 时选择占卜工具（tarot/lenormand/liuyao）
    
-   **divination**：本地抽牌，保证确定性
    
-   **narration**：LLM 把抽牌结果转成自然语言解释
    
-   **persist**：记录对话、解读结果与 trace
    

## **3\. 双模式逻辑（聊天 / 占卜）**

-   默认是**自动判断**：LLM 或规则判断这次是否需要占卜
    
-   如果用户点击\*\*“占卜”按钮\*\*，强制走占卜流程
    
-   聊天模式会保留最近 5 条上下文，让对话更自然
    

## **4\. 技术实现重点**

-   **SpoonOS Graph Agent**：用 StateGraph 编排任务
    
-   **LLM 路由**：用于意图、语气、工具选择
    
-   **本地抽牌**：保证可复现，便于调试

Solidity 基础语法学习笔记

1\. Solidity 是什么

Solidity 是一种面向智能合约的高级编程语言，主要用于以太坊及 EVM 兼容区块链（如 Ethereum、BSC、Polygon、Arbitrum 等）。

Solidity 编写的合约在编译后会生成 EVM 字节码，并部署在区块链上，一旦部署，代码逻辑不可随意更改。

智能合约的本质是：

运行在链上的、公开透明、自动执行的程序。

2\. 合约的基本结构

一个标准的 Solidity 合约通常包含以下部分：

SPDX License 标识（声明开源协议）

pragma 版本声明（指定编译器版本）

contract 定义

状态变量

函数（读 / 写）

合约是 Solidity 中的核心单位，类似于面向对象语言中的“类”。

3\. 数据类型

3.1 值类型（Value Types）

整数类型

uint：无符号整数（>= 0）

int：有符号整数

常用且推荐使用 uint256

Solidity 中所有整数都有固定大小，默认使用 256 位以获得最佳性能。

布尔类型

bool

取值为 true 或 false

地址类型

address

用于表示账户或合约地址

常见用法：

msg.sender：当前调用者

address(this)：当前合约地址

3.2 引用类型（Reference Types）

字符串（string）

字符串用于存储文本数据，但在链上操作成本较高，不适合复杂字符串处理。

数组（array）

数组可以是定长或不定长，用于存储同类型数据集合。

动态数组支持 push，但链上遍历数组会消耗较多 Gas。

映射（mapping）

映射是一种键值对结构，类似哈希表：

Key → Value

无法遍历

所有 key 都有默认值

映射是 Solidity 中非常常用的数据结构。

4\. 变量存储位置（Storage / Memory / Calldata）

Solidity 明确区分数据的存储位置：

storage：链上永久存储（最贵）

memory：函数执行期间临时存在

calldata：只读、不可修改、最省 Gas

实践中建议：

函数参数优先使用 calldata。

5\. 函数基础

函数由以下部分组成：

可见性修饰符

状态修饰符

参数

返回值

5.1 函数可见性

public：合约内外都可调用

external：只能从外部调用

internal：当前合约及继承合约

private：仅当前合约

5.2 状态修饰符

view：读取状态，不修改

pure：不读取也不修改状态

payable：允许接收 ETH

6\. 全局变量

Solidity 提供了一些内置全局变量：

msg.sender：调用者地址

msg.value：发送的 ETH 数量

block.timestamp：当前区块时间戳

block.number：当前区块高度

这些变量在权限控制和业务逻辑中非常重要。

7\. 条件判断与循环

条件判断

使用 if / else 进行逻辑分支判断。

循环

支持 for 和 while，但在链上应尽量避免大规模循环，因为循环会显著增加 Gas 消耗。

链上原则：能不用循环就不用循环。

8\. 错误处理机制

Solidity 中主要有三种错误处理方式：

require

用于参数校验和权限判断，最常用。

revert

主动触发回滚，通常用于复杂逻辑判断。

assert

用于检查“理论上永远不应该失败”的情况。

实际开发中 90% 使用 require。

9\. 构造函数（constructor）

构造函数在合约部署时执行，只执行一次。

常用于初始化合约状态，例如设置合约拥有者（owner）。

10\. 修饰器（modifier）

修饰器用于复用函数前后的校验逻辑，常用于权限控制。

特点：

在函数执行前或后自动插入逻辑

\_ 代表原函数主体的位置

11\. 事件（Event）

事件用于记录链上日志，主要作用是：

供前端监听

方便链上数据追踪

不会被合约内部读取

事件是合约与前端交互的重要桥梁。

12\. ETH 接收与转账

使用 payable 修饰函数或地址

合约可以接收和持有 ETH

提现时通常将余额转给指定地址

转账逻辑需要特别注意安全顺序。

13\. 常见安全注意点

重入攻击

错误做法：

先转账 → 再修改状态

正确做法：

先修改状态 → 再转账

整数溢出

从 Solidity 0.8 开始，整数溢出会自动触发回滚，不再需要 SafeMath。

14\. 最小合约模型

一个最简单、最安全的合约通常具备：

明确的状态变量

简单清晰的函数逻辑

必要的 require 校验

尽量少的链上计算

    -   境外平台向境内居民提供服务
        
    -   以虚拟货币为载体的非法集资、传销、洗钱、赌博等
        

核心理解：技术不等于没风险；只要碰到 Token 发行、融资、交易闭环、资金池、推广返利，风险级别会陡增

## 2 核心法律风险地图（按最常见梳理）

### 2.1 代币发行与交易（最典型的高危区）

-   中国法律明令禁止：以 ICO/IEO/IDO 等方式公开融资
    
-   你把 Token 叫积分、凭证、治理也没用
    
    -   只要具备融资功能或可流通性，就可能被认定为非法金融行为
        
-   空投、白名单也可能被穿透认定为融资或募资的一部分
    
-   技术人员参与（代币模型、空投逻辑、合约部署等）也可能被视为共犯：只是写代码不能免责
    

### 2.2 赌博 传销 洗钱（结构决定罪名）

-   赌博风险结构：充值 → 抽奖或随机收益 → 可提现或可转售
    
    -   典型：链游盲盒、转盘、随机掉落 NFT 或 Token 且能提现
        
-   传销风险结构：邀请返利、多级推广、团队计酬、层级返佣
    
    -   常见于 NFT 项目、DAO 拉新、算力挂靠、矿池推广
        
-   洗钱风险高发点：C2C/OTC 出入金、帮人换汇、资金来源不明
    
    -   你可能不知情，但银行卡冻结、被要求退赔、甚至被刑事追责都可能发生
        

### 2.3 场外交易（OTC）与地下换汇风险

-   风险本质：用虚拟货币做桥梁绕过外汇监管
    
-   反复撮合人民币与外币或虚拟币交易，可能触发非法经营外汇业务
    
-   更糟糕：对手资金若涉诈涉赌涉毒，你会被卷入协助洗钱链条
    

### 2.4 民商事争议（合同大概率不被支持）

-   虚拟货币买卖、委托代投等纠纷常被认定为合同无效、风险自担
    
-   代投（帮朋友操作资金）容易引发亏损赔偿、资金去向不明的责任纠纷，甚至被怀疑非法经营或非法集资
    

## 3 全球监管趋势（你需要知道的大方向）

### 3.1 合规化在推进：框架越来越清晰

-   欧盟：MiCA 落地，对稳定币、服务商牌照、资本与流动性要求更明确
    
-   新加坡：更强调 AML/CFT，与 FATF 标准接轨
    
-   美国：稳定币相关立法推进中，核心围绕发行、储备、反洗钱、消费者保护
    

### 3.2 FATF 与 Travel Rule（理解为什么 Web3 合规这么难）

-   FATF：全球反洗钱与反恐怖融资标准制定者
    
-   Travel Rule（旅行规则）：转账超过一定阈值时，VASP 需收集并传递汇款人、收款人信息
    
-   对 DeFi 与 DEX 的挑战：匿名性 + 跨链复杂性 → 风险评估、协作、报告都更难
    

### 3.3 稳定币监管意义（为什么被盯得最紧）

-   稳定币是 DeFi 的基础设施，体量大，若出问题会有系统性风险（UST 崩盘是标志事件）
    
-   监管目标
    
    -   储备真实、透明（保护投资者）
        
    -   防风险传导（金融稳定）
        
    -   防被用于非法活动（AML）
        

## 4 入职 Web3 的劳动关系风险（很多人忽略）

### 4.1 雇佣关系新形态

-   项目常境外注册，远程办公，国内无用工主体
    
    -   可能无法签有效劳动合同
        
    -   五险一金难保障
        
    -   发生争议或工伤维权困难
        
-   EOR（名义雇主）：可缓解部分问题，但劳动关系认定仍要谨慎
    

### 4.2 薪酬结构风险

-   常见：人民币 + Token 或全 USDT
    
-   风险点
    
    -   工资应以法定货币支付（Token 或 USDT 工资属性存在争议）
        
    -   Token 波动甚至归零
        
    -   影响社保基数、经济补偿计算等
        

### 4.3 出金风险（最现实、最常见）

-   C2C/OTC 出金可能遇到涉诈资金 → 银行卡冻结
    
-   高价出 U、协助他人洗钱、绕监管 → 可能触发刑事风险
    
-   建议：与公司协商保留部分法币收入；留存合法来源记录
    

### 4.4 入职前做项目合法性尽调

-   重点问
    
    -   是否面向中国大陆用户
        
    -   Token 分发机制、收益模型
        
    -   是否含返利层级、投资承诺
        
    -   是否存在资金池、提现闭环
        
-   你不是主导方也可能被牵连：整体项目若涉非法金融活动，技术与运营都可能被调查
    

## 5 刑事风险案例（从结构看共性）

### 5.1 开设赌场 赌博

-   特征：平台可投注、可提现、运营推广分工明确
    
-   司法实践常强调：能提现是显著特征
    

### 5.2 非法经营（含换汇、支付结算）

-   用 USDT 做媒介，为客户提供外币与人民币兑换、赚差价与服务费 → 高风险
    

### 5.3 非法吸收公众存款

-   矿机、积分、返利、释放收益 + 可兑换虚拟币 + 可提现 → 极易被认定为变相吸储
    

### 5.4 组织、领导传销

-   层级返利 + 拉人头计酬 + 门槛费或交币入场 → 传销外观特征非常明确
    
-   技术人员若明知层级奖励用于传销仍提供支持，可能被认定为共犯
    

### 5.5 洗钱

-   提供账户、协助兑换、跨境转移、掩饰来源性质 → 都可能触发
    
-   上游犯罪未判决也不影响洗钱认定的逻辑在实践中存在
    

## 6 网络安全风险（Web3 新手的黑暗森林）

结论：多数人以为是被钓鱼，实际是系统性安全习惯缺失

### 6.1 钓鱼（Phishing）

-   伪造邮件或网站：面试通知、奖学金、账号异常
    
-   社群钓鱼：Telegram、Discord 冒充官方
    
-   假客服、假好友：盗号后精准社工
    
-   高危信号：让你点链接、装软件、连接钱包、签名、给助记词或私钥
    

### 6.2 恶意软件 木马（Malware）

-   伪装面试软件、学习资料、破解器
    
-   剪贴板劫持（地址替换）
    
-   浏览器扩展后门
    
-   远程控制、录屏、窃取 Cookie、窃取密码管理器数据
    

### 6.3 社工（Social Engineering）

-   冒充 HR、导师、学长学姐
    
-   群内管理员私聊发内推或表单或验证
    
-   好友求助要求转账或测试链接
    

### 6.4 供应链攻击（第三方依赖）

-   假插件、带后门的开源库、官方渠道被劫持
    
-   经验：只装必要插件，且核验开发者与下载量
    

### 6.5 地址污染 扫描木马

-   复制粘贴地址被替换、输入框监听
    
-   后果：资产转错地址不可逆
    

### 6.6 传统账号安全

-   密码复用、邮箱或 SIM 劫持、没开 2FA → 邮箱一丢，全盘皆输
    

## 7 防护清单（学生版，可直接照做）

### 面试 实习

-   只用 Zoom、Teams、腾讯会议等主流工具，拒装任何专用面试软件
    
-   必须安装时：先虚拟机测试 + 查安全口碑 + 核对权限与摘要
    
-   核实邀请邮箱、域名、联系人，多渠道确认
    

### 奖学金 空投 福利

-   任何要求连接钱包、签名、输入助记词的网页：默认骗局
    
-   空投用测试钱包，主钱包冷存储
    
-   涉缴费或调整先打官方热线复核，核对域名
    

### 社群 私聊

-   不信官方私聊，不点陌生链接
    
-   遇到急转账、帮测试、填表连接钱包必须二次核实
    

### 软件 插件

-   只从官网或官方商店下载
    
-   插件控制在 3 个以内（钱包、密码管理、广告拦截等必要项）
    
-   摄像头、麦克风按需授权
    

### 账号与密码

-   重要账户开启 2FA（优先验证器或硬件密钥）
    
-   密码管理器 + 每站不同强密码
    
-   不在同一浏览器里同时保存助记词与日常 Cookie
    

### 钱包与转账

-   转账前核对地址前 6 位 + 后 4 位
    
-   助记词、私钥离线保存，绝不截图、绝不网盘、绝不发送
    
-   定期检查授权，及时 revoke 不必要授权
    

### 事件响应

-   怀疑被攻击：立刻断网、记录时间点、截图取证，寻求专业支持
    

## 8 扩展阅读与工具（按用途整理）

-   项目方安全手册：SlowMist 区块链安全红手册
    
-   个人自救：Blockchain Dark Forest Selfguard Handbook
    
-   授权管理：[Revoke.cash](http://Revoke.cash)
    
-   钓鱼检测：Scam Sniffer
    
-   密码管理：1Password、Bitwarden
    
-   被黑档案库：SlowMist Hacked
    
-   反钓鱼练习：[unphishable.io](http://unphishable.io)

# AI 辅助搭建 Obsidian 个人知识库

## 一、为什么我们总是「收藏了不看」

### 1\. 信息困境

-   信息分散在各个平台（微信、网页、PDF、PPT）
    
-   难以聚合，无法形成体系
    

### 2\. 传统笔记的三个痛点

-   **整理成本高**：分类、打标签非常耗时
    
-   **结构僵化**：一旦文件夹结构定死，后期修改成本极高
    
-   **孤岛效应**：笔记之间没有连接，无法复用
    

### 3\. 最终结果

-   只有信息堆积
    
-   没有真正的「知识」
    
-   需要一个能自动整理的「外脑」
    

## 二、核心理念：像管理代码一样管理知识

### 1\. 知识库的本质

-   知识库 ≈ 代码库
    
-   本质都是 **纯文本文件**
    
-   通过「链接」而不是「文件夹」建立关系
    

### 2\. Vibe Note-taking

-   从「自己记笔记」
    
-   转变为「操作一个系统」
    

### 3\. 人与 AI 的角色分工

-   **你（Editor）**
    
    -   判断
        
    -   决策
        
    -   拍板
        
-   **AI（Intern）**
    
    -   执行
        
    -   分类
        
    -   整理
        

### 4\. 核心逻辑

-   把 **机械的体力活** 交给 AI
    
-   把 **思考与判断** 留给自己
    

## 三、工具组合：Obsidian + AI Agent

### 1\. Obsidian（知识仓库）

-   Markdown 纯文本，长期可用、AI 天然可读
    
-   本地存储，数据完全属于你
    
-   双向链接 `[[ ]]`，形成知识网络
    

### 2\. AI Agent（知识管家）

-   代表工具：
    
    -   Claude Code
        
    -   Cursor
        
    -   Windsurf
        
    -   Trae
        
-   与 ChatGPT 网页版的本质区别：
    
    -   **可以直接读取 / 修改本地文件**
        
-   核心优势：
    
    -   批量处理
        
    -   告别复制粘贴
        
    -   一次性整理上百、上千条笔记
        

## 四、实操阶段一：原始积累与结构规划

### Step 1：暴力归集

-   把所有资料直接丢进知识库：
    
    -   PPT
        
    -   会议纪要
        
    -   文章
        
    -   零散想法
        
-   原则：
    
    -   **越原始越好**
        
    -   **不要手动预处理**
        

### Step 2：让 AI 规划结构

-   给 AI 的提示示例（思路）：
    
    -   分析这些资料
        
    -   设计合理的文件夹结构
        
    -   将长内容拆分为独立笔记
        
-   AI 可自动完成：
    
    -   创建文件夹
        
    -   重命名文件
        
    -   拆分内容
        

## 五、实操阶段二：建立连接与清洗数据

### Step 3：建立关联

-   指令 AI：
    
    -   自动插入「标签」
        
    -   自动生成「双向链接」
        
-   目标：
    
    -   把孤立信息点，编织成知识网络
        

### Step 4：数据清洗

-   删除重复内容
    
-   统一 Markdown 排版风格
    

### Step 5：缺失信息处理

-   **客观事实**
    
    -   让 AI 联网补全（定义、参数、背景）
        
-   **主观观点**
    
    -   明确标注为「待确认」
        
    -   坚决不让 AI 编造
        

## 六、设计原则：给 AI 写一份「员工手册」

### 1\. 规则文件

-   明确告诉 AI：
    
    -   文件结构
        
    -   命名规范
        
    -   操作流程
        
-   要求：
    
    -   每次干活前先读一遍规则
        

### 2\. 推荐结构流

-   Inbox（入口）
    
-   Thinking（思考）
    
-   Creating（创作）
    
-   Archive（归档）
    

### 3\. 笔记三原则

1.  **独立性**
    
    -   每篇笔记都可以单独阅读
        
2.  **链接入句**
    
    -   链接自然融入句子，而不是堆在文末
        
3.  **观点命名**
    
    -   用「结论式标题」
        
    -   例如：
        
        -   ❌ 关于 AI
            
        -   ✅ AI 是工具，而不是答案
            

## 七、日常使用：像园丁一样维护知识库

### 1\. 日常用法

-   写作辅助：
    
    -   调用旧笔记
        
    -   快速生成初稿
        
-   快速检索：
    
    -   直接问 AI
        
    -   在整个知识库中定位信息
        

### 2\. 园丁模式

-   定期除草：
    
    -   扫描「孤儿笔记」
        
    -   决定：补链接 or 删除
        
-   长期主义：
    
    -   知识库是复利系统
        
    -   用得越久，价值越大
        

## 八、扩展场景：AI Agent 不只是给程序员用

### 1\. 一个判断标准

-   只要涉及 **文件操作**
    
-   都可以交给 Agent
    

### 2\. 常见玩法

-   C 盘清理：
    
    -   扫描大文件
        
    -   识别垃圾文件
        
-   批量整理：
    
    -   重命名下载文件
        
    -   按日期 / 类型归档
        
-   Workflow 自动化：
    
    -   每日抓取资讯
        
    -   自动生成日报
        
    -   写入知识库
        

## 九、打造你的数字分身（Digital Twin）

### 核心回顾

-   收集 → AI 整理 → 链接 → 迭代
    
-   让知识库成为你的「第二大脑」
    

### 进阶方向

-   尝试 Typeless / 语音输入
    
-   从「Vibe Coding」进化到「Speak Coding」

# DApp

## 一、DApp 的实用定义

-   DApp = **需要与区块链进行读 / 写交互的应用**
    
-   判断一个应用是不是 DApp，看两点：
    
    -   是否调用智能合约
        
    -   是否以链上状态作为核心数据
        
-   前端和后端 **可以是中心化的**
    
-   完全去中心化不是目标，**可用性和用户体验更重要**
    

## 二、现实世界中的 DApp 形态

### 1\. 主流 DApp（最常见）

-   智能合约：去中心化
    
-   前端 / 后端：中心化
    
-   通过中心化服务提升查询效率和体验
    
-   代表项目：Uniswap、OpenSea
    

这是当前**工业级 DApp 的主流形态**。

### 2\. 简单 DApp

-   功能集中在：
    
    -   读取资格
        
    -   mint / transfer
        
    -   展示链上资产
        
-   常见于 NFT Mint 页面
    
-   后端逻辑极少或没有
    
-   **非常适合新手入门练手**
    

### 3\. 极端 DApp

-   前端部署在 IPFS
    
-   几乎没有后端
    
-   强抗审查，但访问慢、体验差
    
-   仅用于特殊场景，不是常规选择
    

## 三、DApp 的基本架构

一个完整可用的 DApp 通常包含：

-   **前端**：用户交互界面（Web）
    
-   **后端**：索引、缓存、数据聚合
    
-   **智能合约**：核心业务逻辑（链上）
    
-   **基础设施服务**：
    
    -   IPFS
        
    -   RPC
        
    -   索引服务
        
    -   预言机
        

## 四、关键基础设施说明

### 1\. IPFS

-   去中心化文件存储系统
    
-   基于内容哈希而不是服务器地址
    
-   常用于：
    
    -   NFT 图片
        
    -   NFT Metadata
        
    -   去中心化前端资源
        
-   免费 IPFS 不保证长期存储，通常配合 Pinata / Filecoin 使用
    

### 2\. RPC 服务商

-   为 DApp 提供区块链的 API 接口（JSON-RPC）
    
-   支持：
    
    -   查询账户余额
        
    -   调用合约
        
    -   发送交易
        
-   本质：**区块链世界的 API 网关**
    
-   DApp 使用链，但不需要维护链
    

### 3\. 索引服务

-   解决链上数据「不可自由查询」的问题
    
-   功能：
    
    -   扫描区块
        
    -   解析事件
        
    -   存入数据库
        
-   提供 GraphQL / REST API
    
-   大型 DApp 几乎必不可少
    

### 4\. 预言机（Oracle）

-   将现实世界数据引入区块链
    
-   通过多数据源 + 多节点 + 经济激励保证可信
    
-   主流方案：Chainlink
    
-   常用于价格、清算条件、外部状态判断
    

## 五、推荐技术栈（新手友好）

### 总体原则

# Solidity 智能合约开发入门

## 1\. EVM 基础认知

### 1.1 什么是 EVM

-   EVM（Ethereum Virtual Machine）是以太坊智能合约的**运行环境**
    
-   所有 Solidity 合约最终都会被编译为 **EVM 字节码**
    
-   特点：**栈式虚拟机、单线程、确定性执行**
    

### 1.2 EVM 的四大执行区（非常重要）

-   **Stack**
    
    -   用于指令和临时计算
        
    -   只能存放 256-bit 数据
        
    -   非常快，但空间极小
        
-   **Storage**
    
    -   链上永久存储合约状态
        
    -   Gas 成本最高
        
    -   合约优化的核心目标：**少用 Storage**
        
-   **Memory**
    
    -   函数执行期间的临时内存
        
    -   不上链，函数结束即销毁
        
    -   Gas 成本低于 Storage
        
-   **Calldata**
    
    -   用户调用合约时传入的参数
        
    -   只读，不可修改
        
    -   比 Memory 更省 Gas
        

类比理解：

-   Storage ≈ 硬盘
    
-   Memory / Calldata ≈ 内存
    

## 2\. Gas 成本与优化直觉

### 2.1 Gas 的核心来源

-   计算
    
-   Storage 读写
    
-   合约体积
    

### 2.2 Storage 的 Gas 成本

-   **首次写入 storage**：≈ 20,000 gas
    
-   **修改已有 storage**：≈ 5,000 gas
    

### 2.3 基本优化原则

-   尽量少存
    
-   能用 memory / calldata 就不用 storage
    
-   避免频繁修改链上状态
    

## 3\. Solidity 开发环境

### 3.1 推荐工具

-   **Remix IDE**
    
    -   在线
        
    -   内置虚拟链
        
    -   支持编译、部署、调试
        
    -   可观察 memory / storage 变化
        

### 3.2 Solidity 版本

-   常用版本：`0.8.x`
    
-   示例：`^0.8.20`
    
-   0.8+ 默认包含 **整数溢出检查**
    
-   阅读合约源码时必须注意版本号
    

## 4\. Solidity 数据类型

### 4.1 值类型（Gas 友好）

-   `bool`
    
-   `uint / int`
    
    -   可指定位宽：`uint8 ~ uint256`
        
    -   位宽越小，占用 storage 越少
        
-   `address`
    
    -   表示 EOA 或合约地址
        
    -   不要用 string 存地址
        
-   `bytes32`
    

### 4.2 引用类型（Gas 昂贵）

-   `string`
    
-   动态数组
    
-   `bytes`
    
-   `mapping`
    

### 4.3 mapping 的典型用途

-   余额账本
    
-   授权账本
    
-   权限映射
    

## 5\. ERC20 合约核心结构

### 5.1 ERC20 是什么

-   以太坊**同质化代币标准**
    
-   定义了一组固定接口，保证生态兼容
    

### 5.2 核心链上状态

-   `name`
    
-   `symbol`
    
-   `decimals`
    
-   `totalSupply`
    
-   `owner`
    

### 5.3 两本账本（核心）

-   **余额账本**
    
    -   address → uint256
        
-   **授权账本**
    
    -   owner → spender → allowance
        

## 6\. 构造函数（Constructor）

-   合约部署时执行
    
-   用于初始化链上状态
    
-   只执行一次
    
-   工具类合约可以没有 constructor
    

## 7\. 函数修饰符

### 7.1 可见性

-   `external`：仅外部
    
-   `public`：内外均可
    
-   `internal`：内部 + 子合约
    
-   `private`：仅当前合约
    

### 7.2 状态修饰

-   `view`：读链上状态
    
-   `pure`：不读不写链上状态
    

## 8\. ERC20 核心函数逻辑

### 8.1 transfer

基本步骤：

1.  校验参数（数量、地址、余额）
    
2.  更新余额
    
3.  触发 Transfer 事件
    

### 8.2 approve

-   修改授权账本
    
-   触发 Approval 事件
    
-   是大多数 DeFi 交互的第一步
    

## 9\. Event 事件机制

### 9.1 作用

-   链上 → 链下通信
    
-   区块浏览器、DApp 监听依据
    
-   比直接读 storage 高效
    

### 9.2 常见事件

-   `Transfer`
    
-   `Approval`
    
-   `Mint`
    

### 9.3 indexed

-   最多 3 个 indexed 参数
    
-   用于链下快速过滤
    

## 10\. Mint 与权限控制

-   Mint 通常不能 public
    
-   常见设计：
    
    -   external 函数做权限校验
        
    -   internal 函数做状态修改
        

## 11\. 错误处理

-   `require`
    
    -   常用
        
    -   可带错误字符串（Gas 较高）
        
-   `revert`
    
    -   无字符串，更省 Gas
        
-   `assert`
    
    -   理论上不会失败的逻辑
        
-   **自定义 error**
    
    -   最省 Gas 的现代方案
        

## 12\. 整数溢出与 unchecked

-   Solidity 0.8+ 默认防溢出
    
-   `unchecked {}` 可省 gas
    
-   初学阶段不建议使用
    

## 13\. Modifier 修饰符

### 13.1 作用

-   抽象前置条件
    
-   权限统一
    
-   代码复用
    

### 13.2 常见场景

-   onlyOwner
    
-   nonReentrant
    
-   时间锁
    
-   角色权限控制
    

## 14\. 常见安全问题直觉

-   不明助记词 ≠ 免费钱
    
-   可能是：
    
    -   合约账户伪装
        
    -   权限限制
        
    -   抢跑机器人（Front-running Bot）
        

安全原则：

-   不导入陌生私钥
    
-   查看地址是否为合约
    
-   小额测试
    

## 15\. 扩展生态

-   **OpenZeppelin**
    
    -   审计过的标准合约库
        
-   **可升级合约**
    
    -   Proxy + Logic
        
-   **钻石架构（EIP-2535）**
    
    -   模块化升级

## Web3行业前辈访谈综合总结

### 一、三个角色，三条路径，但指向同一个核心

这几篇访谈分别来自：

### 二、技术向共识：代码只是 30%，剩下是业务与协作

1\. 前端 / 工程视角（Logic & Jason）

**共识点：**

-   写代码只是工程的一部分
    
-   Web3 的难点不在“技术栈”，而在“业务复杂度”
    

**Logic（前端）强调：**

-   Web3 前端 ≠ Web2 前端 + 钱包
    
-   必须理解：
    
    -   钱包连接 / 签名流程
        
    -   Gas、Nonce、滑点、保证金率、风控逻辑
        
-   前端“老手”的标准不是 API 数量，而是：
    
    -   能给多套方案
        
    -   能预判风险
        
    -   能写完整文档并兜底事故
        

**Jason（底层）强调：**

-   Web3 系统本质仍运行在 CPU / IO / 内存之上
    
-   面试更看重：
    
    -   计算机组成原理
        
    -   IO、缓存、内存模型
        
-   底层开发者最大短板不是技术，而是**产品与业务理解**
    

**一句话总结工程侧：**

AI 能写代码，但**看不懂钱、风险和系统后果**

### 三、社区与增长：共识即生产力

2\. 非技术向但高价值路径（Julie）

**核心判断：**

-   Web3 里，**社区 ≈ 共识**
    
-   共识是去中心化世界最稀缺的生产要素
    

**Julie 的方法论：**

-   从 Dirty Work 起步（翻译、纪要、AMA、内容）
    
-   用高频实践快速找到“擅长且有 ROI 的位置”
    

**社区 0 → 1 的关键策略：**

-   任务必须“可感知”（真实链上操作）
    
-   内容要做减法（生活化叙事）
    
-   明确贡献路径（大使 / 激励机制）
    
-   高频互动而非一次性曝光
    

**对 00 / 05 后的建议高度现实：**

-   不拼资源，拼：
    
    -   长板定位
        
    -   持续输出
        
    -   主动连接
        
    -   好奇心驱动
        

### 四、用人方视角：什么才是“靠谱”

3\. Bruce 的招聘与带教总结（极关键）

**靠谱 = 三个关键词：**

1.  **可预期**：说到做到，能管理时间
    
2.  **可沟通**：卡住就同步，不“人间蒸发”
    
3.  **可复盘**：做完能总结，下次不再犯
    

**常见雷区：**

-   临近 deadline 才说做不完
    
-   闷头干活不汇报
    
-   反复犯同一类错误却无反思
    

**非常实用的方法论：**

-   **经验倍数法**：
    
    -   熟悉 ×1.25
        
    -   做过类似 ×1.5
        
    -   完全陌生 ×2
        
-   所有任务都要拆小，并预留 10–15% buffer
    

**用人方真正看重的不是“会不会”，而是：**

> 这个人交给任务，我敢不敢睡觉

### 五、AI 时代的统一判断（所有人高度一致）

**AI 的能力边界：**

-   减少机械劳动（CSS、类型、脚手架、初步诊断）
    
-   无法替代：
    
    -   业务拆解
        
    -   风险判断
        
    -   跨角色协作
        
    -   责任承担
        

**结论非常明确：**

AI 是放大器，不是方向盘

非技术向（社区 / 产品 / 运营）：

1.  从 Dirty Work 快速试错
    
2.  建立个人输出渠道（推特 / 文章 / AMA）
    
3.  把“贡献”做成可量化成果
    
4.  主动连接项目方，而非等机会

# Agentic AI 与 Web3 的融合

只能“说”，不能“做”  
不具备长期记忆  
没有身份，不能代表任何主体行动

### Agentic AI（2026 方向）

具备推理、记忆和工具使用能力  
可以自主执行任务并持续运行  
拥有私有记忆与执行能力  
能够代表某个主体完成真实世界行为

核心转变是从“对话型 AI”走向“行动型 AI”

## 二、一个完整 AI 智能体的三大组成

### 大脑 The Brain

由 LLM 构成  
负责理解意图、规划步骤、生成行动指令  
不直接执行操作

### 记忆 The Memory

基于向量数据库  
通过 RAG 实现长期与短期记忆  
解决传统 LLM 聊完就忘的问题

### 工具 The Tools

API、Function Calling、MCP 等  
让 AI 可以执行代码、调用系统、访问外部世界  
形成“思考 → 行动 → 观察”的循环

### 身份不可验证

缺乏统一的治理与监管框架

本质问题是信任缺失

传统金融体系存在明显不适配

KYC、验证码对机器不友好  
结算速度无法满足毫秒级交互  
微额交易手续费过高

机器经济需要一种原生的支付方式

## Web3 安全与刑事风险

### 一、Web3 当前整体安全形势

1.  总体风险现状  
    2025 年 Web3 领域发生 1200 起以上较严重安全事件，总损失金额超过 35 亿美元。  
    攻击呈现两种并行趋势：  
    一是“精准猎杀”，二是“广撒网攻击”。  
    整体特点是事件频发、手段复杂，对行业安全构成长期威胁。
    

### 二、两类核心攻击模式

1.  精准猎杀（低频但高损失）  
    主要目标是 CEX、DeFi 项目、核心开发者和管理员账户。  
    常见方式包括社会工程、私钥和热钱包窃取、深度合约漏洞利用，部分案件具有国家级黑客背景。  
    特点是攻击周期长、策划精细、单笔损失巨大，往往伴随复杂洗钱流程。
    
2.  广撒网攻击（高频但单笔金额较小）  
    最常见的三类是私钥窃取、钓鱼攻击和 Rug Token 跑路项目。  
    随着 AI 技术普及，钓鱼内容高度拟真，普通用户更难分辨，Rug 项目也呈现团队化、流水线化趋势。
    

### 三、AI 时代下的攻击新变化

攻击方式呈现明显的技术融合趋势。  
攻击者会将协议机制漏洞、合约缺陷、供应链漏洞与 AI 自动化工具结合使用。  
典型表现包括：  
利用计算精度漏洞攻击 DeFi 合约；  
在 npm、GitHub 依赖中投毒；  
滥用新 EIP 特性；  
使用 Deepfake 进行身份伪装和社交工程。

### 四、Web3 在中国刑事风险高发的原因

核心原因在于法律体系与技术理念的不匹配。  
中国采用中心化法律体系，而 Web3 强调去中心化。  
同时行业认知不足、监管滞后，司法实践中容易采用“结果倒推社会危害性”的方式定性。  
本质问题是用旧框架评价新技术。

### 五、最容易触发刑事风险的行为场景

高风险行为主要集中在以下方面：  
出入金相关行为，如 OTC、U 商、搬砖套利；  
项目方发币、拉人头、返佣和邀请机制；  
KOL 荐币、带单；  
合约交易被认定为赌博；  
挖矿或 DePIN 项目涉及传销式结构。

### 六、合约交易与赌博的核心区分逻辑

赌博的本质是以赌注押注不确定结果，赌注代表预期收益或损失，输赢与真实市场价格无关。

合约交易的核心特征是：  
资金用于购买具有真实价值的虚拟资产；  
盈亏取决于市场价格涨跌、开仓价格和杠杆倍数；  
平台只收取固定手续费，不与用户对赌。

因此，合约交易在本质上更接近金融衍生品，而非赌博行为。

### 七、GoPlus 给出的安全建议要点

对个人用户而言：  
不点击不明链接、不随意签名和授权；  
私钥和助记词绝不联网；  
只通过官方渠道下载钱包；  
签名前逐字核对交易内容。

对项目和生态而言：  
开发阶段要安全前置，引入审计和自动化安全工具；  
运行阶段进行全链路监控；  
建立应急响应机制；  
在协议层面强化原生安全设计。

# Web3 运行原理

## 一、Web3 到底在解决什么问题？

**核心问题：**

在没有中心化机构的情况下，

如何确认“你是谁”

如何保证“账本可信”

如何让“规则自动执行”

**Web3 的答案：**

-   私钥 & 数字签名 → 身份与授权
    
-   去中心化网络 + 共识 → 可信账本
    
-   智能合约 → 自动执行规则
    

* * *

## 二、钱包、私钥、助记词：Web3 的身份系统

### 1\. 三者关系

-   **私钥（Private Key）**
    
    -   资产和权限的唯一控制权
        
    -   区块链世界的“终极印章”
        
    -   丢了 ≈ 永久丢失（无法重置）
        
-   **助记词（Seed Phrase）**
    
    -   私钥的可读备份
        
    -   可以派生多个账户
        
-   **地址（Address）**
    
    -   公钥哈希后的字符串
        
    -   不是隐私，只是公开收款号
        
    -   行为可被链上分析关联
        

### 2\. 核心认知

-   区块链 **不认识人**
    
-   只认识：**谁能签名**
    
-   谁掌握私钥，谁就拥有资产与权限
    

### 3\. 私钥的社会学意义

-   任何人都可以随机生成私钥
    
-   不需要审批、身份、国家、机构
    
-   **个人主权的起点**
    
-   权利不是被“发放”的，而是自己生成的
    

* * *

## 三、交易（Transaction）是什么？

### 1\. 一笔交易包含什么？

交易 = 要做的事 + Gas Fee + Nonce

-   要做的事：转账 / 调用合约 / mint / 投票
    
-   Gas Fee：为网络资源付费 + 激励
    
-   Nonce：防止同一交易被重复执行
    

### 2\. 钱包真正做的事

-   组装交易数据
    
-   用私钥签名（授权）
    
-   广播到区块链网络
    

钱包不是“记账者”，只是“签名器 + 发信人”

* * *

## 四、数字签名：Web3 信任的根基

### 数字签名能保证什么？

-   任何人都可以验证交易是你发的
    
-   任何人都无法伪造你的签名（除非有私钥）
    

信任来自 **密码学**，不是机构

* * *

## 五、Gas Fee：为什么必须存在？

### Gas 的三层作用

1.  **防垃圾交易**
    
    -   提高作恶成本
        
2.  **激励节点/验证者**
    
    -   提供算力、带宽、维护网络
        
3.  **经济闭环**
    
    -   使用资源 → 付费 → 网络可持续
        

没有激励的去中心化系统无法长期运行

* * *

## 六、一笔交易是如何“跑起来”的？

### 从交易到出块的完整流程

Wallet（签名）  
→ RPC / Node（传播）  
→ Mempool（排队）  
→ Builder / Validator（挑选）  
→ Block（出块）  
→ Explorer（可查）

### 为什么需要“确认时间”？

-   区块像账本的一页
    
-   新区块引用旧区块 hash
    
-   越往后，历史越难被推翻
    
-   PoS 下有 Finality（最终确认），约 12–13 分钟
    

**不可篡改 ≠ 立刻不可改**

* * *

## 七、共识机制：全球陌生人如何记同一本账？

### PoW（工作量证明｜BTC）

-   拼算力
    
-   能耗高
    
-   规则简单、历史最久
    

### PoS（权益证明｜ETH）

-   质押 + 随机选验证者
    
-   更节能
    
-   作恶会被罚没质押资产
    

共识的本质：让作恶成本远高于收益

* * *

## 八、钱包 ≠ 网络：RPC 是现实中的风险点

### 真实关系

-   钱包通常只连一个 RPC
    
-   RPC 背后是节点或节点集群
    
-   RPC 是常见的“中心化入口”
    

### 抗审查来自哪里？

-   可换钱包
    
-   可换前端
    
-   可换 RPC
    
-   可换节点
    

**替换性 = 抗审查能力**

* * *

## 九、智能合约：链上的“自动执行规则”

### 智能合约是什么？

-   写在区块链里的可执行代码
    
-   在 EVM 中运行
    
-   由交易触发
    
-   自动改变链上状态
    
-   一旦部署，难以随意更改
    

### Code is Law 的含义

-   规则透明、可验证
    
-   执行历史可追溯
    
-   减少中介与信任成本
    

从“信人 / 信机构”  
转向“信代码 + 共识 + 治理”

* * *

## 十、区块链协议如何升级？（以太坊）

### EIP 流程

1.  社区讨论（论坛）
    
2.  形成提案文档（EIP）
    
3.  社区共识
    
4.  硬分叉升级（每年 1–2 次）
    

关键点：

-   没有 CEO
    
-   没有拍板人
    
-   协议是被治理的代码
